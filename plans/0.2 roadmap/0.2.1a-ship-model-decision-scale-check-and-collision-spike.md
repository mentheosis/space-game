# 0.2.1a Implementation Plan: Ship Model Decision, Scale Check, and Collision Spike

## 1. Goal

Run a short, practical spike before committing to detailed ship collision implementation.

This phase should answer:

- Is the current ShuttleA visual model usable as the 0.2 ship model?
- Is the ship scaled plausibly for the player, cockpit, hatch, and future interior?
- Which collision approach works best for the current ship in Godot?
- Can the player stand on a landed/frozen ship `RigidBody3D` without unacceptable instability?
- What measurable acceptance criteria should drive the next sub-phases?

This phase should produce knowledge, not final collision polish.

## 2. Timebox

Target timebox:

- 1 working day or less.

Suggested split:

- 1 hour: current model/scene audit.
- 1 to 2 hours: scale-reference setup and cockpit/hatch sizing check.
- 3 to 4 hours: collision experiments.
- 1 hour: notes, recommendation, and next-plan updates.

If the spike reveals a blocker, stop and document it rather than trying to solve the whole collision system inside the spike.

## 3. Current Decision

Use the current OpenGameArt `ShuttleA.obj` as the 0.2 ship model unless the scale check reveals a serious problem.

Expected outcome:

- Keep ShuttleA.
- Adjust scale/offset if needed.
- Build a repeatable ship integration process around it.

Fallback outcomes:

- Keep ShuttleA for exterior only, defer believable cockpit/interior scale.
- Scale ShuttleA before further collision work.
- Reject ShuttleA only if cockpit/hatch scale is impossible or collision fitting is clearly impractical.

## 4. Scope

### In Scope

- Inspect current ship scene hierarchy.
- Inspect current visual model transform and rough dimensions.
- Add temporary scale reference helpers.
- Check cockpit/canopy, hatch, and player clearance.
- Try experimental collision shapes on the current ship.
- Try at least one broad compound primitive approach.
- Try a simple collision-mesh or convex-shape approach if practical.
- Test player standing on the landed ship.
- Record what works and what breaks.
- Produce recommendations for 0.2.1b and 0.2.1c.

### Out of Scope

- Final ship collision.
- Final hatch.
- Final cockpit/interior.
- Replacing the ship model unless the check clearly rejects ShuttleA.
- Full moving-platform behavior.
- Standing on the ship while flying.
- Planet prop collision.
- Long-term multi-ship data model implementation.

## 6. Step-by-Step Process

## Step 1: Current Ship Audit

### Tasks

- Inspect `Ship.tscn`.
- List visual nodes.
- List physical collision nodes.
- List interaction `Area3D` nodes.
- List interior/context volumes.
- List marker nodes.
- Record current ship visual transform:
  - position,
  - rotation,
  - scale.
- Record current known gameplay dependencies:
  - hatch positions,
  - interior spawn,
  - exterior exit,
  - seat anchor,
  - ship camera,
  - flight/landing behavior.

### Output

Short notes answering:

- What collision exists now?
- Which collision is only for interior walking?
- Which collision is exterior/ship-body collision?
- Which nodes must not move without retesting entry/exit/seat behavior?

### Checklist

- [ ] Current ship visual transform recorded.
- [ ] Current collision nodes listed.
- [ ] Current interaction volumes listed.
- [ ] Current marker dependencies listed.
- [ ] Risky nodes identified.

## Step 2: Scale Reference Setup

### Goal

Check whether the current ship visual scale can plausibly contain the player and future cockpit/interior work.

### Tasks

- Create a temporary player scale reference.
- Include:
  - player capsule proxy,
  - eye-height marker,
  - seated cockpit envelope proxy,
  - hatch clearance proxy,
  - 1m and 2m measuring bars.
- Place the reference near:
  - cockpit/canopy area,
  - hatch/entry area,
  - likely interior path,
  - top hull/walkable exterior surface.

### Reference Dimensions

Existing player capsule:

- radius: `0.35`
- height: `1.8`

Recommended clearance targets:

- standing/cabin height: `2.0` to `2.2`
- walkable path width: `0.9` or more
- hatch opening proxy: at least player capsule width plus clearance
- cockpit seated envelope: enough for seat, eye point, and canopy clearance

### Questions To Answer

- Does the cockpit/canopy look large enough for a seated player?
- Could the current ship plausibly have an interior/cockpit that matches the exterior?
- Is the hatch area large enough to support believable entry later?
- Does the player look absurdly large or small next to the ship?
- Should the ship visual scale change before collision work continues?

### Checklist

- [ ] Player scale reference created.
- [ ] Cockpit/canopy checked.
- [ ] Hatch area checked.
- [ ] Broad exterior surface scale checked.
- [ ] Decision recorded: keep scale, adjust scale, or flag scale risk.

## Step 3: Collision Experiment A - Compound Primitives

### Goal

Test whether hand-authored primitive/convex compound shapes can approximate the ship well enough.

### Tasks

- Add temporary collision shapes for major ship regions:
  - fuselage,
  - wings/side structures,
  - cockpit/canopy mass,
  - underside/landing area,
  - top hull walkable surface,
  - stern/hatch area.
- Keep interaction volumes separate.
- Keep current hatches and markers working.
- Use Godot collision debug view for visual fit.

### Tests

- Start on foot near ship.
- Walk around ship exterior.
- Try to stand on top/broad hull.
- Jump from hull to ground.
- Enter ship.
- Sit.
- Take off.
- Land.
- Exit.

### Notes To Capture

- Which shapes fit well?
- Which shapes create invisible walls?
- Which seams snag the player?
- Does the player jitter while standing?
- Does this approach seem maintainable for future ships?

### Checklist

- [ ] Primitive fuselage approximation tested.
- [ ] Primitive wing/side approximation tested.
- [ ] Primitive top walkable surface tested.
- [ ] Hatch/seat/flight retested.
- [ ] Problems recorded.

## Step 4: Collision Experiment B - Collision Mesh / Convex Approach

### Goal

Determine whether a collision-only mesh or convex-shape workflow is worth using for higher fidelity.

### Tasks

- Try a quick collision-only mesh if practical.
- Options:
  - use Godot-generated convex collision on a duplicate/simple mesh,
  - create a rough low-poly collision mesh,
  - import a simplified OBJ/GLB collision proxy,
  - use a combination of generated convex pieces and primitives.
- Compare against compound primitives.

### Cautions

- Do not use raw high-detail render mesh collision for the dynamic ship.
- Do not spend the spike modeling final collision.
- Stop if the workflow becomes expensive or unclear.

### Notes To Capture

- Is the workflow faster or slower than primitives?
- Is collision more stable?
- Is the player less likely to snag?
- Does it work with the ship as `RigidBody3D`?
- Would this be repeatable for future ships?

### Checklist

- [ ] Collision mesh or convex approach attempted, if practical.
- [ ] Stability compared against primitive approach.
- [ ] Workflow cost recorded.
- [ ] Recommendation recorded.

## Step 5: Landed Ship Standing Test

### Goal

Check the key physics assumption: the player can stand on a landed/frozen ship body.

### Test Cases

- Stand still on broad ship surface for at least 5 seconds.
- Walk forward/back across ship surface.
- Walk across a seam between collision shapes.
- Jump while standing on ship.
- Fall/step from ship to ground.
- Enter ship after standing on exterior.
- Take off after exterior traversal.

### Acceptance Notes

Record whether:

- standing is stable,
- player jitters,
- player slides unexpectedly,
- player is launched,
- player gets stuck,
- ship reacts physically when it should be frozen,
- player can recover to normal movement.

### Checklist

- [ ] Standing test completed.
- [ ] Walking test completed.
- [ ] Seam test completed.
- [ ] Jump/fall test completed.
- [ ] Entry/flight retest completed.
- [ ] Recommendation recorded.

## Step 6: Measurement and Acceptance Criteria Draft

### Goal

Convert spike observations into concrete criteria for 0.2.1b and 0.2.1c.

Draft acceptance criteria should include:

- max acceptable collision overhang from visible hull,
- minimum cockpit/hatch scale confidence,
- minimum stable standing time,
- required ship traversal route,
- hatch/seat/flight regression checks,
- debug-view review requirements.

Suggested initial criteria:

- [ ] Player stands on hull for 5 seconds without falling through.
- [ ] Player walks hatch-area to cockpit/top-hull route.
- [ ] Player jumps from hull to ground without launch/stuck bugs.
- [ ] Collision debug view shows major collision within `0.5m` of visible hull on important surfaces.
- [ ] No major collision shape extends beyond visible hull by more than `0.3m` unless documented.
- [ ] Ship entry, seat, takeoff, landing, stand, and exit still work.

These should be adjusted based on actual spike findings.

- Cockpit/interior scale risk.
- Hatch scale risk.

Recommended location:

```text
plans/0.2 roadmap/0.2.1a-spike-results.md
```

### Decision Options

Ship model:

- Keep ShuttleA.
- Keep ShuttleA with scale adjustment.
- Keep ShuttleA for exterior only.
- Reconsider ship model before 0.2.1b/0.2.1c.

Collision strategy:

- Compound primitives.
- Collision-only mesh.
- Hybrid primitives plus collision meshes.
- Defer high-fidelity collision pending model change.

Physics strategy:

- Landed/frozen ship supports exterior standing well enough.
- Landed ship needs special static collision mode.
- Exterior standing is unstable and needs deeper movement/physics work.

## 7. Definition of Done

0.2.1a is complete when:

- The current ship model has been explicitly accepted, adjusted, or rejected for 0.2 work.
- Cockpit/hatch/interior scale has been checked against the player.
- At least one compound primitive collision experiment has been tested.
- A collision mesh or convex workflow has been considered or briefly tested.
- Landed-ship standing behavior has been tested.
- Entry, seat, takeoff, landing, stand, and exit have been retested after experiments.
- Spike findings are written down.
- The detailed 0.2.1b and 0.2.1c implementation plans can be written from actual findings instead of assumptions.

## 8. Non-Goals

Do not turn this spike into full implementation.

Specifically, do not:

- Polish final collision.
- Fully reorganize the ship scene unless required for testing.
- Build final hatch/cockpit art.
- Add planet object collision.
- Add new ship assets.
- Add a multi-ship data system.
- Spend more than the spike timebox unless a clear blocker is found.
