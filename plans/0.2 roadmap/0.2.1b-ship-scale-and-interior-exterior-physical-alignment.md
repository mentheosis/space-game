# 0.2.1b Implementation Plan: Ship Scale and MVP Interior

## 1. Goal

Build the first MVP-quality ship interior that physically and visually belongs inside the current ShuttleA exterior.

This phase is no longer a temporary greybox cleanup. The target is an immersive, high-quality prototype interior for a polished video game ship:

- plausible scale relative to the player,
- interior geometry that matches the exterior model,
- cockpit/cabin layout that feels intentional,
- transparent cockpit/window treatment where practical,
- a more believable pilot chair,
- better floor, wall, ceiling, panel, and lighting detail,
- materials and textures that move beyond placeholders,
- preserved enter/sit/fly/land/stand/exit gameplay.

This is still an MVP prototype, not final production art. It should establish the quality bar and workflow for future ship interiors.

## 2. Achievability Assessment

This is achievable now as an MVP vertical slice if we make the right tradeoffs.

Achievable in this phase:

- A cohesive cockpit/cabin interior that fits the exterior better.
- Substantially better geometry than the current rectangular shell.
- Custom or kitbashed pilot chair.
- Window/cockpit glass treatment that visually connects inside and outside.
- Better materials, lighting, and readable controls/panels.
- Correct marker placement and preserved gameplay.

Not realistic in this phase:

- Final AAA-quality authored ship interior.
- Fully animated hatch and production-grade door mechanism.
- Fully interactive cockpit instrumentation.
- Complete multi-ship interior framework.
- Perfect exterior/interior continuity for every model detail.
- Final collision for the full exterior hull.

The right target is: **MVP-quality, visibly intentional, and good enough that 0.2.1c can fit exterior collision around a stable ship scale and interior layout.**

## 3. Inputs From 0.2.1a

The spike showed:

- ShuttleA is a good visual direction.
- Standing on a landed ship is stable enough to proceed.
- Primitive collision works for broad physical masses.
- Swept wings and tail likely need convex/collision-only meshes later.
- The cockpit/canopy and current interior feel too small relative to the player.
- The current interior shell clips through or conflicts with the exterior visual model.
- Hatch entry, sitting, and ship flight remained stable during spike tests.

0.2.1b should solve the scale/interior mismatch before 0.2.1c fits exterior collision.

## 3.2 Alignment Feedback Loop

The first implementation pass showed that hand-authored scene edits are not enough for the quality target. 0.2.1b now includes an automated static alignment report so future iterations are driven by mesh-derived evidence.

Run:

```bash
scripts/ship_alignment_report.sh
```

Output:

```text
reports/ship_alignment_report.md
```

The report currently checks:

- transformed ShuttleA visual mesh bounds,
- slice-by-slice hull width and height along the ship length,
- a heuristic forward upper cockpit/canopy mesh slice,
- heuristic cabin, floor/walk-path, and rear hatch fit targets,
- ship collision shape bounds,
- interior/detail mesh bounds,
- authored interior OBJ asset presence and scene references,
- required measured fit-comparison inputs,
- glass/canopy mesh positions relative to the cockpit candidate,
- collision and interior protrusion outside the visual model's broad AABB,
- top-projection empty-space estimates for broad rectangular bounds.

For validation gating, run:

```bash
python3 tools/ship_alignment_report.py --check
```

The check mode fails if:

- required authored interior OBJ files are missing, too small to be useful, or not referenced by `Ship.tscn`,
- required fit targets or comparison nodes are missing,
- required authored interior meshes disappear from the report,
- collision or interior/detail bounds protrude outside the ShuttleA visual AABB,
- canopy alignment drifts beyond the measured cockpit/canopy target,
- floor alignment drifts beyond the measured walk-path target.

It also generates projection diagrams:

```text
reports/ship_alignment_top.svg
reports/ship_alignment_side.svg
reports/ship_alignment_front.svg
reports/ship_hull_profile.csv
reports/ship_fit_targets.json
reports/ship_fit_recommendations.md
reports/ship_fit_recommendations.json
reports/ship_alignment_dashboard.html
```

These diagrams overlay:

- gray points: transformed ShuttleA OBJ vertices,
- red boxes: collision shapes,
- blue boxes: interior/detail meshes,
- cyan boxes: glass/canopy pieces,
- orange box: heuristic cockpit/canopy mesh slice.

This is still not sufficient for final visual judgment because AABB checks cannot prove curved/swept surface fit. The next efficient step is to add host-side screenshot capture with fixed exterior and interior debug cameras, then iterate from both screenshots and the static alignment report.

Screenshot capture has been added.

Run on the host:


This command:

Screenshots are written into the project report folder:

Iteration rule:

- If the static report says a collision or interior piece exceeds the visual AABB, fix that before aesthetic tuning.
- If the hull profile shows a shape is being evaluated against a broad rectangular section, add a more specific mesh slice, authored marker, or generated fit target before trusting the number.
- If the top-projection empty-space estimate is high for a fitted piece, replace the broad box with a more specific authored mesh, convex hull, or split part.
- If a future script needs the measured geometry data, read `reports/ship_fit_targets.json` instead of scraping `reports/ship_alignment_report.md`.
- If `reports/ship_fit_recommendations.md` lists an `adjust` row, use that as the next measured placement change before subjective polish.
- If `reports/ship_fit_recommendations.md` lists a `review` row, inspect fixed screenshots before applying the suggested move.
- Use `reports/ship_alignment_dashboard.html` as the primary review surface because it combines gate state, measured recommendations, projection overlays, and fixed-camera screenshots.
- If the projection SVGs show a major top/side/front mismatch, fix the scene from the measured projection before screenshot polish.
- If screenshots show a mismatch that AABB checks miss, prefer adding a more specific mesh slice/marker/report check over another hand-tuned coordinate change.
- If a piece must be hand-authored for quality, move toward reusable mesh assets or generated mesh files rather than growing `Ship.tscn` indefinitely.

Remaining 0.2.1b alignment process:

1. Generate the report, SVGs, hull profile, fit-target JSON, fit recommendations, dashboard, and screenshots.
2. Resolve any `adjust` rows in `reports/ship_fit_recommendations.md` that can be fixed from measured bounds.
3. Review `reports/ship_alignment_dashboard.html` for any `review` rows before applying subjective vertical, visibility, or readability changes.
4. For each mismatch, add or tighten a measurable report check first when practical.
5. Adjust authored OBJ assets, scene transforms, or markers.
6. Re-run the alignment gate, recommendation tool, and capture script.
7. Only accept the phase after both automated checks and rendered review agree that scale, glass, hatch, cockpit, and interior placement are coherent.

## 5. Design Principles

### Interior Must Fit The Exterior

The interior should not feel like a rectangular room hidden inside an unrelated model.

It should:

- follow the ship's narrow cockpit/cabin proportions,
- respect the nose, canopy, hatch, and tail direction,
- avoid visible clipping through the exterior shell,
- place the pilot seat where the cockpit visually suggests it belongs,
- make windows/cockpit glass spatially meaningful.

### Quality Over Placeholder Breadth

Prefer a smaller, better interior over a larger greybox room.

Good:

- compact cockpit/cabin,
- well-shaped floor and walls,
- believable chair,
- strong lighting,
- clear hatch and seat path,
- coherent materials.

Bad:

- large rectangular room,
- flat untextured walls,
- interior protruding through exterior,
- cockpit that cannot visually fit the player,
- panels and props scattered without layout purpose.

### Author Custom Geometry Where Fit Matters

Open assets are still useful, but this interior must match the chosen ship.

Recommended:

- custom simple geometry for cockpit shell, floor, ribs, hatch frame, and chair base,
- open/CC0 textures for metal, rubber, glass, panels, and floor,
- human-reviewed external assets only for reusable cockpit props or chair/details if they fit.

## 6. Asset Strategy

## 9. Risks

### Risk: This Expands Too Much

Mitigation:

- Target one compact high-quality interior slice.
- Prioritize cockpit, seat, floor, walls, hatch frame, and lighting.
- Defer interactive instruments and final hatch animation.

### Risk: Scaling Breaks Existing Markers

Mitigation:

- Adjust hatch, seat, camera, and exit markers in the same phase.
- Run validation immediately after scale changes.

### Risk: Interior Still Cannot Plausibly Fit

Mitigation:

- Treat the ship as a compact cockpit/cabin craft.
- Consider modest visual scale increase.
- Avoid preserving the old rectangular interior dimensions.

### Risk: External Assets Do Not Match

Mitigation:

- Prefer custom geometry for layout-critical pieces.
- Use external assets only after review.
- Use open textures more freely than open geometry.

### Risk: Larger Ship Feels Worse To Fly Or Land

Mitigation:

- Keep scale changes modest.
- Do not retune flight unless necessary.
- Record flight/landing issues separately.
