# 0.2.1 Multi-Phase Plan: Physical Collision and Traversal Fidelity

## 1. Ambitious Target

0.2.1 is the physical-fidelity foundation for the 0.2 roadmap.

The goal is not merely to add a few safer collision shapes. The goal is to make the ship, large props, and landmarks feel like believable physical objects at player scale.

The long-term target for this 0.2.1 program is:

- The current shuttle visual model is treated as the first serious ship integration target.
- The ship exterior feels like a real physical object.
- Most ship surfaces that visually appear walkable are walkable or fail in a believable way.
- The player can move around the landed ship exterior with reasonable fidelity to the visible model.
- Collision closely approximates the visible ship without relying on fragile raw render mesh collision.
- The cockpit/interior scale is checked before collision is overfit to the current model.
- Ship scale and the physical interior/exterior relationship are improved before final exterior collision fitting.
- The integration process is repeatable for future ships.
- Planet props, rocks, pads, and landmarks use collision quality that matches their visual importance.
- Small decorative clutter does not create invisible snags.
- Future ship hatch, cockpit, interior, and planet-detail work builds on this framework.

## 2. Ship Model Decision

For 0.2, use the current OpenGameArt `ShuttleA.obj` as the primary ship visual model.

Rationale:

- The model is visually good enough to justify real integration work.
- Replacing it now would delay collision and traversal progress.
- The project eventually wants multiple ships, so this should become the first example of a reusable ship-integration process, not a one-off hardcoded solution.

Important constraint:

- Collision, markers, camera targets, hatches, cockpit positioning, and seat placement may be ShuttleA-specific in the ship scene.
- Core gameplay code should not assume ShuttleA-specific dimensions directly.
- Future ships should be able to provide their own visual scene, collision proxy, marker set, and tuning data through the same scene conventions.

## 3. Cockpit and Interior Scale Check

Before fitting final-ish collision to the ship model, verify whether the visual model is scaled plausibly for the player.

This check belongs in the first spike phase because it affects:

- ship visual scale,
- collision scale,
- hatch position,
- cockpit position,
- interior/cockpit layout,
- seat placement,
- third-person camera framing,
- future transparent cockpit work.

### Scale Reference

Use the existing player as the scale reference.

Current player collision:

- Capsule radius: `0.35`
- Capsule height: `1.8`

Recommended clearance targets:

- Standing/cabin height: at least `2.0` to `2.2` meters.
- Standing shoulder width clearance: at least `0.9` to `1.2` meters.
- Walkable path width near hatch/cockpit: at least `0.9` meters.
- Seated cockpit envelope: enough room for a seat, camera/eye point, and forward visibility without clipping the canopy.

These do not need to be final real-world dimensions, but they should prevent obviously impossible interiors.

### Scale Check Method

Add a temporary scale-check setup during the spike:

- A visible player capsule reference.
- An eye-height marker.
- A seated/cockpit envelope proxy.
- A hatch clearance proxy.
- Optional measuring bars for 1m, 2m, and player height.

Place these around the visible ship model to answer:

- Does the cockpit/canopy appear large enough for the player?
- Could a believable seat fit under the canopy?
- Is the hatch large enough for player entry?
- Does the current visual model need to scale up or down?
- Would scaling the model break landing footprint, flight feel, or camera framing?

### Scale Decision Output

The spike should produce one of these decisions:

1. **Keep current visual scale.**
2. **Adjust ship visual scale before collision work continues.**
3. **Keep visual scale but treat the ship as mostly cockpit-only, not a walkable interior.**
4. **Defer interior fidelity and only solve exterior physicality for now.**
5. **Reject current model scale and reconsider ship model choice.**

The expected outcome is likely option 1 or 2, but the check should happen before detailed collision authoring.

## 4. Why Split 0.2.1 Into Sub-Phases

The plan should be ambitious, but collision implementation needs empirical feedback. Godot collision behavior, especially `CharacterBody3D` standing on a landed/frozen `RigidBody3D`, should be tested before we over-specify the final solution.

The recommended structure is:

- **0.2.1a: Ship Model Decision, Scale Check, and Collision Spike**
- **0.2.1b: Ship Scale and Interior/Exterior Physical Alignment**
- **0.2.1c: Ship Exterior Collision and Traversal Pass**
- **0.2.1d: Reusable Ship Collision Integration Pattern**
- **0.2.1e: Planet Object and Landmark Collision**
- **0.2.1f: Validation, Debugging, and Polish**

This is intentionally less gate-heavy than the prior audit/proxy/walkable/refinement split. The ship collision work should happen iteratively, informed by a short spike.

## 5. Quality Bar

### Ship Collision Quality Bar

Expected:

- The collision footprint follows the visible ship silhouette much better than the old box shell.
- The player can stand on broad hull surfaces, wings or shoulders, landing structures, and other surfaces that visually imply support.
- Sloped surfaces behave reasonably: shallow slopes are traversable, steep slopes slide or block naturally.
- Hatch and cockpit areas feel spatially aligned with the model.
- Collision seams do not create frequent snagging.
- Player movement over the ship does not jitter badly while the ship is landed.
- Collision work remains compatible with a future multi-ship setup.

Not required yet:

- Standing on the ship while it is flying.
- Perfect polygon-accurate collision.
- Full moving-platform behavior.
- Final hatch/cockpit geometry.
- Final ship model replacement.

### Planet Object Collision Quality Bar

Expected:

- Large rocks, pads, ramps, and landmarks have authored collision.
- Objects that look climbable or standable generally support the player.
- Small clutter is usually non-colliding.
- Collision is smooth enough to avoid snagging.
- Collision categories are documented and repeatable.

Not required yet:

- Fully procedural terrain collision.
- Collision for every tiny visual detail.
- Final planet biome asset set.

## 6. Measurable Acceptance Criteria

The detailed implementation plans should prefer measurable checks over vague language.

Candidate criteria:

- Player can stand on the landed ship hull for at least 5 seconds without falling through or jittering badly.
- Player can walk from the hatch-side area toward the cockpit/top hull without falling through the ship.
- Player can walk around the landed ship perimeter without major invisible blocking.
- Player can jump from hull to ground without launch/stuck bugs.
- Player can stand on at least one large planet object.
- Collision debug view shows primary collision generally within `0.5m` of the visible hull for important exterior surfaces.
- No major collision shape extends beyond visible geometry by more than `0.3m` unless documented as intentional.
- Hatches, seat, exit, takeoff, landing, and flight still work after collision changes.

These numbers may be tuned after the spike, but the plan should keep objective targets.

## 7. Sub-Phase Overview

## 0.2.1a: Ship Model Decision, Scale Check, and Collision Spike

### Goal

Learn the actual collision constraints before writing a detailed ship collision pass.

### Scope

- Confirm ShuttleA remains the 0.2 ship model.
- Measure/check current ship visual scale against the player capsule.
- Test whether cockpit/canopy scale can plausibly contain the player or a seated cockpit.
- Try compound primitive collision on the current ship.
- Try imported/simple collision mesh approaches if quick enough.
- Test `CharacterBody3D` standing on a landed/frozen `RigidBody3D`.
- Note what breaks: jitter, sliding, snagging, hatch interference, flight issues.
- Decide which scale/interior concerns should drive 0.2.1b and which collision-authoring strategy should drive 0.2.1c.

### Timebox

Recommended: 1 working day or less.

The spike is not meant to produce final collision. It should produce knowledge.

### Deliverables

- Scale-check notes.
- Collision experiment notes.
- Recommendation for collision strategy:
  - compound primitives,
  - Blender-authored collision meshes,
  - hybrid approach.
- First list of measurable acceptance criteria, adjusted from actual findings.
- Decision on whether ship visual scale changes before further collision work.

### Definition of Done

- We know whether the current ship scale is plausible.
- We know whether broad landed-ship standing works with the current physics setup.
- We know which collision strategy is worth pursuing.
- We have enough information to write the detailed implementation plan for 0.2.1b and outline the collision strategy for 0.2.1c.

## 0.2.1b: Ship Scale and Interior/Exterior Physical Alignment

### Goal

Fix the ship scale and physical interior/exterior relationship enough that collision work is not built around a visibly implausible cabin or cockpit.

### Why This Exists

The 0.2.1a spike showed that the current shuttle visual direction is good, but the cockpit/canopy and interior relationship look too small relative to the player. If we ignore that, we risk fitting exterior collision to a ship scale that will be revised soon after.

This phase should not produce final cockpit art or hatch animation. It should produce a physically plausible ship scale and interior/cockpit envelope for the next collision pass.

### Scope

- Decide whether to scale the current ShuttleA visual model up.
- Reposition or resize temporary interior floor, walls, seat, hatch markers, and camera markers as needed.
- Establish a plausible physical cockpit/cabin envelope inside the exterior model.
- Reduce or remove interior geometry that visibly clips through the exterior model.
- Separate interior collision from exterior collision more clearly.
- Preserve current gameplay loop:
  - enter,
  - sit,
  - pilot,
  - stand,
  - exit,
  - fly,
  - land.
- Keep final hatch model, transparent cockpit, and detailed cockpit visuals deferred to 0.2.2.

### Deliverables

- Ship scale decision applied or explicitly deferred.
- Revised interior/cockpit physical envelope.
- Updated hatch/seat/marker positions if needed.
- Reduced interior/exterior clipping.
- Notes for 0.2.2 visual cockpit/hatch work.

### Definition of Done

- The player no longer looks obviously oversized relative to the cockpit/cabin envelope.
- The temporary interior no longer visibly fights the exterior model.
- Hatch, seat, stand, exit, flight, and landing still work.
- The next exterior collision pass can fit around a more plausible ship scale.

## 0.2.1c: Ship Exterior Collision and Traversal Pass

### Goal

Build the first serious ship exterior collision implementation around the chosen scale and collision strategy.

### Scope

- Build a collision proxy that approximates the full visible ship exterior.
- Represent the major ship forms:
  - fuselage,
  - wings/side structures,
  - cockpit region,
  - hatch/stern area,
  - underside/landing structures,
  - broad top surfaces.
- Make landed exterior traversal broadly possible.
- Tune slopes, seams, and surface transitions.
- Preserve hatch, seat, interior, flight, landing, and camera behavior.

### Deliverables

- Revised ship collision hierarchy.
- Broad walkable landed ship exterior.
- Collision fit notes against visible model.
- Manual traversal route around the ship.

### Definition of Done

- The ship no longer feels like an invisible box.
- Player can traverse most visually plausible landed ship surfaces.
- Collision mismatch is acceptable for an immersive prototype.
- Existing ship interactions and flight still work.

## 0.2.1d: Reusable Ship Collision Integration Pattern

### Goal

Turn the ShuttleA integration into the first example of a repeatable multi-ship process.

### Scope

- Define required ship scene structure.
- Define visual/collision/marker conventions.
- Define per-ship marker requirements:
  - hatch,
  - interior spawn,
  - exterior exit,
  - seat anchor,
  - seat exit,
  - cockpit/camera target,
  - landing reference.
- Define collision proxy requirements.
- Decide whether ship-specific tuning should live in exported properties, child marker nodes, or a future ship definition resource.

### Deliverables

- Ship integration conventions.
- Updated ship scene organization if needed.
- Notes for adding a second ship later.

### Definition of Done

- ShuttleA-specific work is not hidden inside generic gameplay code.
- A future ship can follow the same integration checklist.
- The project has a repeatable collision-fitting process.

## 0.2.1e: Planet Object and Landmark Collision

### Goal

Apply the same collision philosophy to planet objects, landmarks, rocks, and landing pads.

### Scope

- Categorize existing props and landmarks.
- Add collision to major standable objects.
- Remove or avoid collision on small decorative clutter.
- Improve landing pad collision.
- Improve large rock collision.
- Improve landmark collision where the player can reach it.
- Establish collision conventions for future biome assets.

### Candidate Objects

- Planet B landing pad.
- Large rock clusters.
- Planet A launch landmark.
- Planet B mineral arch.
- Future imported rocks or terrain props.

### Deliverables

- Walkable landing pad collision.
- Walkable large rock or terrain prop collision.
- Landmark collision examples.
- Prop collision category notes.

### Definition of Done

- Large objects can be stood on when they visually support it.
- Small decorative objects do not snag the player.
- Collision quality feels consistent across the ship and planet surfaces.

## 0.2.1f: Validation, Debugging, and Polish

### Goal

Make collision quality repeatable and protect it from regressions.

### Scope

- Add collision/traversal validation scene.
- Add automated checks where stable.
- Add manual traversal checklist.
- Add debug documentation.
- Add review criteria for future collision assets.
- Update validation script if automated checks are added.

### Validation Targets

Automated validation should cover:

- Player can be placed on a ship exterior surface.
- Player becomes grounded.
- Player remains above the surface briefly.
- Player can move across an authored surface.
- Player can stand on at least one planet object.
- Existing ship entry/flight/landing validation still passes.

Manual validation should cover:

- Full exterior walkaround.
- Jumping on and off ship surfaces.
- Hatch interaction after exterior traversal.
- Flight after collision changes.
- Landing after collision changes.
- Walking on selected planet props.
- Checking for snagging on decorative clutter.

### Deliverables

- Validation scene or extended validation.
- Manual test route.
- Collision debug checklist.
- Updated `scripts/validate.sh` if applicable.

### Definition of Done

- Collision improvements are testable.
- Manual review can clearly identify regressions.
- The phase can be safely built on by ship hatch/cockpit and planet detail phases.

## 8. Full 0.2.1 Completion Criteria

0.2.1 as a whole is complete when:

- Ship model scale is checked against player/cockpit requirements.
- Ship scale and temporary interior/cockpit physical envelope are improved enough for collision work.
- Ship collision closely follows the visible model at player scale.
- The landed ship exterior is broadly traversable.
- Most surfaces that visually look walkable behave believably.
- The player can stand and move on selected planet objects and landmarks.
- Small decorative clutter does not create annoying collision.
- Hatches, seat, ship interior context, flight, landing, and exit still work.
- Collision authoring conventions are documented and proven.
- The collision process can be repeated for future ships.
- Automated and manual validation cover the main traversal paths.
- The collision framework is ready for hatch animation, transparent cockpit, richer ship detail, and larger planet detail.
