# 0.2.1c Implementation Plan: High Quality Modeling Workflow

## 1. Goal

Create a real modeling workflow for production-direction ship interiors and exterior/collision alignment.

0.2.1b proved that procedural OBJ generation is useful for measurement and rapid iteration, but it is not enough for the visual target. The next goal is to establish a repeatable Blender-to-Godot pipeline that can produce a high quality ShuttleA interior prototype, then reuse that process for future ships.

The target is not final AAA asset completion in one pass. The target is a professional workflow that can plausibly reach that bar:

- Blender source files are the art source of truth.
- The ShuttleA exterior is imported as a reference mesh.
- Interior shell, cockpit canopy fit, floor, ribs, dashboard, seat, hatch frame, and collision proxies are authored against that reference.
- Export/import into Godot is automated and reproducible.
- Alignment screenshots, high-fidelity walkthrough MP4s, and PNG contact sheets remain the review gate.
- External asset use remains human-reviewed before adoption.

## 2. Blender Licensing

Blender is free and open-source software. Blender itself is released under the GNU GPL. Artwork and game assets created with Blender are not automatically GPL-licensed just because Blender was used to create them.

Practical impact for this project:

- We can use Blender without buying a license.
- We can commit project-authored `.blend` files if we choose.
- We can export meshes/materials for our Godot game.
- We still need to track the license of any external models, textures, add-ons, scripts, or kitbash packs we import.

## 6. Asset Authoring Rules

### Blender Scene Collections

Use named collections:

- `Reference_Exterior`: imported ShuttleA visual reference, not exported as interior.
- `Interior_Render`: visible interior meshes exported to Godot.
- `Interior_Glass`: canopy glass and transparent cockpit pieces.
- `Collision_Proxy`: simplified collision meshes or collision guide surfaces.
- `Markers`: hatch, seat, pilot eye, camera, exit, and alignment markers.
- `Review_Cameras`: fixed cameras matching our Godot screenshot angles where useful.

### Geometry Standards

- No paper-thin visible ribs. Structural pieces need believable thickness.
- No floating detail blocks unless they read as intentional mounted components.
- The cockpit canopy must be modeled as a curved fighter-style dome fitted to the ShuttleA exterior canopy material region.
- The hatch-to-seat path must be enclosed and readable from player height.
- The chair must have a protected player volume; the player/camera must not clip through it.
- Interior floor and side wall surfaces must fit inside the exterior shell with visual margin.

### Materials

- Prefer a small set of reusable Godot materials for the MVP.
- Use Blender materials as semantic labels during export, but keep final runtime material tuning in Godot unless the glTF material is clearly better.
- Avoid high-frequency procedural noise that shimmers or reads as broken geometry in the walkthrough.

## 7. Export Pipeline

Create a headless export script:

```bash
"$BLENDER_BIN" --background assets/source/blender/ships/shuttle_a/shuttle_a_interior.blend \
  --python tools/blender/export_shuttle_a.py
```

The export script should:

- validate required collections exist;
- hide or exclude `Reference_Exterior`;
- export `Interior_Render` and `Interior_Glass` to `shuttle_a_interior.glb`;
- export `Collision_Proxy` to `shuttle_a_collision.glb` or another agreed collision artifact;
- write marker transforms to `shuttle_a_markers.json`;
- fail if required named objects or markers are missing;
- write a log into `reports/ship_modeling/`.

The bootstrap/export workflow should also preserve reference-fit measurements
when the chosen exterior model exposes useful semantic materials. ShuttleA has
a `Cockpit` material region, so the workflow records its transformed ship-space
bounds in `reports/ship_modeling/shuttle_a_reference_fit.json` and derives the
first canopy shell from those bounds instead of relying only on hand-tuned
coordinates.

Godot import should then produce a stable scene or mesh resource consumed by `Ship.tscn`.

## 10. Iteration Process And Review Gate

Each modeling iteration should be a focused art pass, not a broad "make the
interior better" pass. The purpose is to make defects easier to see, fix, and
regress-test.

The iteration cadence must favor larger, reviewable steps over tiny visual
nudges. Before starting a render/check cycle, the agent must post a short
status note in chat with:

- The named pass.
- The specific defects being attacked.
- The expected visible delta.
- The acceptance checks that will decide whether the pass is worth showing.

During longer modeling work, the agent should continue posting progress updates
at natural checkpoints, especially before changing direction. The user should
be able to tell whether the work is progressing toward a named pass target,
debugging a failed render, or reconsidering the approach.

Avoid presenting new review media when the only changes are subtle coordinate tweaks
unless that media answers a specific alignment question. A normal review cycle
should change one meaningful layer of the ship, such as the canopy/cockpit
composition, the corridor enclosure, material hierarchy, chair clearance, or
structural rib language.

For the current 0.2.1c objective, "large enough" usually means a pass changes
the player-readable architecture of the ship, not just trim density. Examples
of sufficiently large passes:

- Close obvious missing floor, wall, ceiling, or canopy-liner gaps.
- Rebuild the cockpit approach path so the player reaches the raised pilot
  position by a believable ramp, step, or platform instead of an isolated chair
  post.
- Reposition or redesign the chair, dashboard, and pilot-eye framing so the
  player can see past the chair and through the forward canopy.
- Replace a broad flat wall/side surface with a coherent molded interior shell
  that follows the exterior shuttle volume.
- Replace a placeholder chair, console, or canopy frame with a new authored
  form that changes silhouette and use-read, not only surface detail.

Examples that are not large enough on their own while architectural defects
remain:

- Adding bolts, labels, small light strips, or vents.
- Moving a rail or panel by a few centimeters.
- Tuning a material color without changing the underlying spatial read.
- Adding detail to cockpit edges while the floor, wall enclosure, ramp/access,
  or forward sightline is still broken.

Small coordinate or material adjustments are still allowed, but they should be
batched into a larger pass and reviewed together. If the agent finds itself
making multiple tiny changes without a visible improvement, it should stop,
explain the issue, and propose a bigger workflow/tooling correction before
continuing.

Priority order for choosing the next pass:

1. **Interior enclosure and completeness:** close square floor holes, missing
   wall spans, missing ceiling and overhead shell, missing canopy liner, and any
   broken-open areas that make the ship feel non-physical. This is the first
   priority until the interior reads as a complete enclosed volume in both the
   walkthrough and manual game view.
2. **Playable collision verification:** confirm the player can walk through the
   interior, ascend the cockpit ramp/platform, approach the chair, and return
   without falling through, clipping through stairs/floors/walls, or snagging on
   placeholder collision. Collision should support the intended authored
   surfaces rather than relying on hidden flat floors.
3. **Material depth and realistic lighting:** improve material variation,
   roughness contrast, darker recessed areas, rubber/metal separation, edge
   definition, and reduce flat grey. Replace broad/glowy placeholder lighting
   with smaller, more believable local light sources and practical fixtures.
4. **Cockpit canopy fit:** improve the interior canopy framing and liner so it
   matches the exterior fighter-jet-style dome more closely.
5. **Cockpit platform and seat integration:** make the chair, footwell,
   dashboard, side consoles, and platform feel like one designed pilot station.
6. **Rib/frame quality:** replace simple tube-like supports with more
   believable structural frames, brackets, bevels, and attachment logic.

When choosing a pass, the agent should select the highest-priority visible
defect from this list. If a lower-priority detail pass seems tempting, the
agent must first check whether any higher-priority defect remains obvious in
the latest walkthrough/cockpit review.

Recommended iteration loop:

1. Choose one explicit target, such as canopy fit, cockpit transition cleanup,
   floor/wall enclosure, seat clearance, rib thickness, material breakup, or
   collision/visual alignment.
2. Make the Blender source change in `tools/blender/bootstrap_shuttle_a_scene.py`
   or directly in the `.blend` once the authored-file workflow becomes primary.
3. Run `bootstrap ShuttleA Blender scene` when the bootstrap script changes.
4. Run `validate ShuttleA modeling workflow` to export, import, build, and
   capture review media.
5. Generate or inspect the latest walkthrough MP4/contact sheet before showing
   the result to the user.
6. Generate or inspect the dedicated cockpit/seated-view MP4/contact sheet when
   the pass touches the canopy, console, chair, pilot-eye position, or forward
   exterior sightlines.
7. Compare the result against the strict review checklist below.
8. Only present review media as a candidate when it passes the agent-side check
   well enough to be worth human review.

Agent-side review checklist for every visual iteration:

- The hatch-to-seat route reads as an enclosed physical interior, not a set of
  floating panels or open transparent gaps.
- No arbitrary square frames, panels, or detail blocks clip through the player
  path, chair, canopy, floor, or exterior shell.
- The front pilot view reads as a smooth curved fighter-style canopy fitted
  forward and overhead into the ShuttleA exterior, not as a rectangular window
  or archway.
- The cockpit volume is positioned in the forward canopy section of the model,
  not in the neck/corridor section.
- Visible structural ribs, hoops, rails, and consoles have believable thickness,
  bevels, and material contrast; they must not read as paper-thin flat strips.
- The chair protects the player/camera volume; pilot view and walkthrough
  capture must not clip through the chair.
- Material and color breakup should support a serious first art prototype:
  panels, recesses, screens, trim, glass, floor, and structural members should
  read as distinct surfaces.
- Build/import success alone is not acceptance. The visual artifact must pass
  this checklist before the pass is considered ready for user review.

If an iteration fails the checklist, continue iterating before presenting it
unless the failure reveals a planning or tooling decision that needs user input.

Required larger-pass cadence:

1. **State pass intent in chat before editing.** Example: "Cockpit artifact cleanup and canopy
   composition pass: remove over-bright streaking, reduce intrusive side shell
   panels, and improve the pilot-chair-to-dome read."
2. **State why this pass is the highest-priority next pass** under the priority
   order above.
3. **Make a material/geometry change large enough to be visible in the contact
   sheet.**
4. **Post a progress update before rendering** that explains what changed and
   what the render is expected to prove.
5. **Run the full Blender/Godot validation profile.**
6. **Inspect contact sheets locally before presenting media.**
7. **Post the self-review result**: passed, failed, or partially passed, with
   the reason.
8. **Present the MP4/contact sheet only when the result meets the pass-specific checks, or
   report why it failed and what the next larger pass will change.**

The agent should not silently run several render/check cycles. Each cycle needs
an explicit progress note so the user can understand whether the iteration is
advancing, debugging, or circling.

### Current 10-Iteration Lighting And Material Sprint

Goal: improve ship interior lighting and material readability while preserving
a dark sci-fi mood. The target is not to make the cabin broadly brighter or to
copy a specific reference image's panel design. Use the references for
realistic light direction, localized practical sources, surface response,
material contrast, and readable shadow detail. The player should be able to
read the floor path, wall structure, cockpit route, pilot seat, ramp/stairs,
and major interactable shapes without relying on broad ambient wash.

Iteration limit:

- The sprint has a hard cap of **10 meaningful render iterations**.
- A meaningful iteration must make a visible lighting/material change large
  enough to evaluate in the MP4 or contact sheet.
- Do not spend iterations on tiny color nudges, isolated trim changes, or
  unreviewable coordinate tweaks while larger lighting/material defects remain.
- Before each iteration, state the pass target, why it is the highest-priority
  next lighting/material defect, and what the review media should prove.
- After each iteration, self-review the MP4/contact sheet against the criteria
  below and state whether the result passed, partially passed, or failed.
- Stop before iteration 10 if the criteria are met. Stop at iteration 10 even
  if more polish is possible, then summarize remaining risks instead of
  continuing silently.

Acceptance criteria:

- **Readable dark mood:** The cabin remains dark and atmospheric, but no main
  walkthrough segment is dominated by unreadable black. Route edges, main wall
  masses, cockpit approach, and major surfaces remain visible.
- **Practical light logic:** Bright areas have obvious nearby sources: low
  side/floor lights, small cabin lamps, cockpit displays, ceiling practicals,
  or visible instrument glow. Avoid light that appears to come from nowhere.
- **Floor path readability:** The central walking path and floor panel grid are
  readable from hatch to cockpit, including seams, panel changes, ramp/stair
  transitions, and cockpit threshold.
- **Controlled floor reflectivity:** Floor panels catch light with subtle
  sheen and roughness variation, but do not become mirror-like, wet-looking, or
  noisy.
- **Localized pools:** Lights create localized pools and gradients across the
  floor, walls, ribs, and cockpit surfaces instead of flat global brightness.
- **Shadow detail:** Dark recesses remain dark, but wall panels, ribs, rail
  shapes, equipment bays, and ceiling structure still have silhouette
  separation.
- **Material separation:** At walkthrough distance, dark metal, coated wall
  panels, rubber/gaskets, seat fabric, glass, floor panels, screens, and small
  emissive indicators read as distinct material families.
- **No color wash regression:** The red exterior light remains blocked from
  the interior except where it would be physically visible through openings or
  windows.
- **No texture sparkle:** Roughness, normal, and procedural texture changes
  must not create glittering speckles, shimmer, or high-frequency crawling in
  motion.
- **Gameplay clarity:** Entry, walking route, ramp/stairs to cockpit, pilot
  seat, and exit path remain visually navigable in the walkthrough.
- **Collision unchanged unless needed:** Do not add new wall/floor collision
  changes in this lighting/material sprint unless a visual change creates a
  traversal bug.
- **Evidence:** Produce a named 720p MP4 and PNG contact sheet after each
  meaningful iteration. The final sprint pass must have the host validation
  profile passing.

## 11. Acceptance Criteria

0.2.1c is complete when:

- Blender is installed and documented for macOS/Linux use.
- `BLENDER_BIN` is documented and consumed by repo scripts.
- A ShuttleA `.blend` source file exists with named collections and exterior reference mesh.
- A headless Blender export creates Godot-consumable `.glb` artifacts.
- Godot imports and displays the Blender-authored interior.
- Existing hatch, seat, stand, exit, and flight flow still works.
- Walkthrough MP4/contact sheet shows an enclosed hatch-to-seat route without visible broken geometry.
- Pilot view looks through a curved canopy fitted to the exterior model.
- Dedicated cockpit review media shows the chair, side consoles, dashboard,
  canopy, planet sightline, and tower sightline without camera clipping or
  misleading stale output.
- Static and host validation scripts pass.
- The workflow is documented well enough to repeat for a second ship later.
