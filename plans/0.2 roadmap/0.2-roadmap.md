# 0.2 Roadmap: Fidelity, Collision, and Immersion

## Goal

Version 0.2 should move the project from a mechanics prototype with improved art toward a more immersive vertical-slice foundation.

The main goals are:

- Better collision fidelity and traversal.
- A ship whose visible model, physical model, interior, hatch, and cockpit feel like one coherent object.
- More detailed planets with richer geometry, surface materials, biomes, and landmarks.
- A higher art-quality bar that no longer treats assets as quick placeholders.

We should still prefer free open-source assets and self-authored assets, but the selection bar is higher now. External assets should be reviewed by the human before import when they meaningfully define the look of the game.

## Guiding Principles

### 1. Collision Is Gameplay, Render Geometry Is Presentation

Render meshes should not automatically become gameplay collision.

Use:

- Simple primitive or convex compound collision for dynamic objects.
- Authored simplified collision for walkable props and ship surfaces.
- Static concave collision only for fixed environment pieces where appropriate.
- Separate scene nodes and naming for visual geometry and collision geometry.

Avoid:

- Raw high-detail render meshes as dynamic collision.
- Collision that is much larger than the visual model.
- Decorative geometry that blocks movement unpredictably.

### 2. Hero Assets Need Custom Integration

The ship is now a hero asset. It should not remain a downloaded model wrapped around unrelated box collision.

The ship should have:

- Matching exterior silhouette and collision footprint.
- Walkable exterior surfaces where visually appropriate.
- A usable hatch that visibly opens and closes.
- Transparent cockpit glass.
- Interior/cockpit layout that matches the exterior model.
- Clear entry, seat, and exit points.

### 3. Planets Need Systems, Not Just Decorations

Planet detail should scale beyond hand-placed props.

We need conventions for:

- Surface material regions.
- Biome identity.
- Local terrain features.
- Landmark placement.
- Surface prop density.
- Collision policy for rocks, pads, ruins, and natural formations.
- Performance and level-of-detail expectations.

### 4. Asset Sourcing Requires Review Gates

Open-source assets are still preferred, but not all free assets fit the project.

Before importing a meaningful external model pack, we should review:

- License and attribution requirements.
- Visual fit.
- Polygon density.
- Material quality.
- Scale and pivot quality.
- Availability of glTF/GLB/FBX/OBJ source.
- Whether collision can be authored cleanly.
- Whether the asset is generic filler or a visual identity piece.

Human review is required before importing new external assets for:

- Ship exterior or interior.
- Cockpit.
- Hatches and doors.
- Major planet landmarks.
- Biome-defining rocks, plants, ruins, or structures.

CC0 textures and generic material sets can be imported with normal ledger tracking.

## Recommended Order

The best order is:

1. Physical collision and traversal fidelity.
2. Ship visual integration, hatch, and cockpit.
3. Planet scale and terrain framework.
4. Planet detail and biome art pass.
5. Immersion polish and vertical-slice review.

This order keeps us from placing polished visuals on top of incorrect physical behavior. It also separates the ship's physical fidelity from its later visual/interior fidelity.

## Phase 0.2.1: Physical Collision and Traversal Fidelity

### Purpose

Make collision and traversal feel physically believable at player scale. This phase owns the physical side of the ship exterior, walkable ship surfaces, object collision, and traversal validation.

### Scope

- Define collision-authoring conventions.
- Audit current collision layers, masks, shapes, triggers, and interaction volumes.
- Separate visual mesh, walkable collision, blocking collision, trigger volumes, interaction volumes, and interior/context volumes.
- Replace broad ship collision with a higher-fidelity compound collision approach.
- Check current ship visual scale against the player, cockpit, hatch, and future interior requirements.
- Make the landed ship exterior broadly traversable wherever the visual model suggests the player should be able to stand.
- Improve collision seams, slopes, and transitions across the ship exterior.
- Make selected planet objects, props, pads, and landmarks standable or blocking as appropriate.
- Establish collision categories for future imported/custom assets.
- Add debug, validation, and manual test coverage for traversal.

### Relationship To 0.2.2

0.2.1 owns the **physical** ship exterior:

- collision shape,
- walkable surfaces,
- traversal,
- slope/seam behavior,
- prop collision policy.

0.2.2 owns the **visual and interaction presentation** of the ship:

- hatch model and animation,
- cockpit glass,
- exterior visual detail,
- interior/cockpit coherence,
- materials and lighting,
- visual interaction feedback.

### Deliverables

- Collision architecture and audit.
- Higher-fidelity ship collision proxy.
- Broad walkable landed ship exterior.
- Higher-fidelity collision refinement where needed.
- Planet object and landmark collision examples.
- Traversal validation and manual review checklist.
- Detailed sub-phase plans for `0.2.1a` through `0.2.1e`.
- A repeatable ship collision/integration pattern for future ships.

### Definition of Done

- The landed ship exterior feels broadly physical and traversable.
- Most surfaces that visually appear walkable behave believably.
- Ship collision closely follows the visible model without relying on fragile raw render mesh collision.
- The player can stand and move on selected planet objects and landmarks.
- Small decorative objects do not create annoying collision snags.
- Ship entry, seating, flight, landing, and exit still work.
- Collision authoring conventions are ready for later ship and planet detail work.
- Ship-specific collision and markers are integrated in a way that can be repeated for future ships.

## Phase 0.2.2: Ship Visual Integration, Hatch, and Cockpit

### Purpose

Turn the ship from a physical prototype into a visually coherent hero asset. This phase focuses on exterior detail, hatch presentation, cockpit glass, and the relationship between exterior and interior spaces. It builds on the physical collision work from 0.2.1 instead of redefining it.

### Scope

- Add an open/close hatch model or animation.
- Make hatch state visible from outside and inside.
- Add transparent cockpit glass.
- Align cockpit position with the exterior model.
- Improve exterior surface materials, hull panels, thrusters, landing structures, and cockpit silhouette.
- Improve pilot seat placement.
- Make the interior feel connected to the exterior shell.
- Add simple cockpit geometry visible from outside through glass.
- Review whether the current OpenGameArt ship remains the base, is modified, or is replaced.
- Review whether the interior should remain physically walkable or become a focused cockpit space for now.

### Technical Notes

- Hatch interaction should remain reliable before animation complexity grows.
- The hatch should not create collision traps.
- Cockpit glass should use a material that is readable but not too expensive or visually noisy.
- We should avoid a huge ship interior unless the ship model scale truly supports it.
- Major replacement ship assets require human review before import.

### Deliverables

- Hatch scene/component.
- Hatch open/closed state.
- Transparent cockpit material.
- Improved ship exterior visual detail.
- Cockpit/interior alignment pass.
- Updated ship interaction prompts and tests.

### Definition of Done

- Entering the ship has a visible hatch interaction.
- The player understands where the cockpit is from outside.
- The ship exterior has a stronger material and silhouette identity.
- The pilot seat is spatially plausible.
- The old placeholder interior/box feeling is substantially reduced.

## Phase 0.2.3: Planet Scale and Terrain Framework

### Purpose

Prepare planets for larger, more detailed surfaces without turning every planet into hand-placed one-off geometry.

### Scope

- Decide target planet scale increase for the next playable slice.
- Re-tune gravity, ship speeds, landing distances, and travel readability if planet size changes.
- Define surface placement conventions for larger planets.
- Add local terrain feature support around authored points of interest.
- Define biome/material region strategy.
- Decide whether planet surfaces remain smooth spheres with placed terrain or move toward generated/displaced terrain.
- Add tools or helper scripts for placing surface-aligned objects.

### Recommended Approach

Do not jump directly to fully procedural terrain.

First:

- Increase planet scale modestly.
- Keep spherical planet bodies.
- Add authored local terrain clusters and biome regions.
- Improve material variation.
- Build placement tools and conventions.

Then evaluate whether procedural or mesh-displaced terrain is necessary.

### Deliverables

- Planet scale recommendation.
- Gravity/travel tuning notes.
- Surface placement framework.
- Biome/material region plan.
- Local terrain feature examples.

### Definition of Done

- Larger planets remain navigable.
- Landing is still practical.
- Surface features can be placed predictably.
- Planet detail work can proceed without ad hoc placement every time.

## Phase 0.2.4: Planet Detail and Biome Art Pass

### Purpose

Make planets feel like distinct places rather than decorated spheres.

### Scope

- Add higher-quality rocks, mineral formations, terrain props, and landmarks.
- Add biome-specific material variation.
- Add more realistic object placement density.
- Improve Planet A and Planet B visual identity.
- Add large silhouettes visible from flight.
- Add smaller details visible on foot.
- Improve landing areas.
- Apply the established 0.2.1 collision policy to new detail assets.

### Asset Strategy

Use external assets for:

- Generic rocks.
- Ground materials.
- Mineral/terrain props.
- Small surface debris.

Prefer custom assets for:

- Major landmarks.
- Ruins or signal structures.
- Planet-identity silhouettes.
- Any object central to exploration.

Human review required before importing:

- Major landmark packs.
- Biome-defining model packs.
- Any non-CC0 asset requiring attribution.

### Deliverables

- Planet A biome/detail pass.
- Planet B biome/detail pass.
- Landmark and prop asset ledger updates.
- Collision implementation per prop category using the 0.2.1 policy.
- Surface readability review from walking and flight distances.

### Definition of Done

- Planet A and Planet B are visually distinct.
- Important landmarks are readable from the ship.
- Ground-level exploration has meaningful visual variety.
- Detail does not interfere with movement, landing, or ship takeoff.

## Phase 0.2.5: Immersion Polish and Vertical-Slice Review

### Purpose

Bring the improved collision, ship, and planet work together into a coherent playable slice.

### Scope

- Improve lighting consistency across ship, planet surfaces, and space.
- Add basic hatch/ship interaction audio if appropriate.
- Add simple visual feedback for landing, hatch use, and cockpit state.
- Review UI scale, prompts, and ship HUD placement after visual changes.
- Add performance checks for imported assets and larger planets.
- Create a 0.2 manual review route.

### Deliverables

- 0.2 playable review scene.
- Manual test route:
  - Walk on planet.
  - Approach ship.
  - Stand on ship/object.
  - Enter via hatch.
  - Pilot from cockpit.
  - Fly to second planet.
  - Land.
  - Exit and explore detailed surface.
- Performance notes.
- Asset ledger complete for 0.2.

### Definition of Done

- The prototype feels substantially more physical and immersive.
- Ship and planets no longer read as disconnected placeholder systems.
- Collision supports player expectations.
- Asset sourcing and custom art conventions are ready for future phases.

## Asset Review Workflow

For each external asset candidate:

1. Add the candidate to an asset review note with source URL, license, preview image, and intended use.
2. Confirm license and attribution requirements.
3. Review visual fit with the current project.
4. Check file format and import quality.
5. Estimate cleanup work.
6. Human approves or rejects.
7. Import approved assets into a source folder.
8. Create Godot wrapper scenes.
9. Add collision manually.
10. Update `assets/ASSET_LEDGER.md`.

No major external model should bypass this process.

## Recommended Immediate Next Step

Start with **Phase 0.2.1: Physical Collision and Traversal Fidelity**.

Reason:

- The ship visual/collision mismatch is already visible.
- Standing on objects is a core player expectation.
- Better ship detail depends on knowing how the ship collision will be authored.
- Planet detail will also need a reliable prop collision policy.

The first detailed implementation plan should cover **0.2.1a: Ship Model Decision, Scale Check, and Collision Spike**.
