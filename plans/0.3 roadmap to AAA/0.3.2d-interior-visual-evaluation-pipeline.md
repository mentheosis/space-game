# 0.3.2d Interior Visual Evaluation Pipeline

## Objective

Build a repeatable evaluation pipeline that can inspect the prototype shuttle interior holistically instead of relying primarily on a few screenshots or walkthrough camera angles.

The goal is to catch visual-design failures before human review:

- floating decorative objects
- unanchored panels, lights, rails, and detail pieces
- lights with no believable visible source
- geometry that looks decorative but has no physical or functional reason
- surfaces that are too flat, too noisy, or insufficiently separated by material family
- cockpit/cargo/ramp regions that only look acceptable from favorable angles

The walkthrough and contact sheets should remain human-facing evidence, but they should become the final review layer, not the main method of discovering basic coherence problems.

## Problem Statement

The recent multi-iteration art loop produced many small changes, but the result still does not read as professional or realistic enough.

The failures are process failures as much as asset failures:

- screenshot evidence hides problems outside the chosen camera views
- moving walkthroughs reveal only a narrow path through the ship
- generated detail can float or fail to connect to surrounding structure
- lighting can appear arbitrary unless checked against visible fixtures
- small decorative additions can create visual noise without improving design quality
- no current tool asks whether a detail is physically mounted, supported, or functionally justified

The next production step should therefore be an evaluation pipeline, not another decorative art pass.

## Source Of Truth

The authored Blender source remains the source of truth:

- `assets/source/blender/ships/prototype_shuttle/prototype_shuttle.blend`

The pipeline should inspect the Blender source first, then optionally inspect exported GLB/Godot evidence.

This is important because many visual problems are spatial/modeling problems that can be detected before export.

## Evaluation Layers

### 1. Object Classification

Every authored interior object should be classified into a design role.

Initial categories:

- `walkable_surface`
- `wall_panel`
- `ceiling_panel`
- `structural_rib`
- `trim_or_gasket`
- `rail_or_handle`
- `light_fixture`
- `emissive_lens`
- `display_or_control`
- `seat_component`
- `mechanical_component`
- `cargo_fixture`
- `decorative_or_unknown`

Classification can start from object names and collections, then improve with metadata later.

Acceptance:

- no significant visible object remains `decorative_or_unknown` unless it is explicitly reviewed
- every object has an intended physical/design role

### 2. Surface Attachment Audit

Each non-primary object must be attached to, embedded in, or supported by a larger parent surface or structure.

For each detail object, compute:

- nearest larger surface
- distance to that surface
- whether the object intersects, touches, floats above, or is buried inside it
- whether the object orientation agrees with the local surface normal or expected mounting axis
- whether there is an obvious mounting relationship such as a bracket, backplate, frame, socket, rail, hinge, or panel recess

Initial thresholds:

- `PASS`: detail is touching/intersecting a plausible parent surface by 0-3 cm
- `WARN`: detail is 3-8 cm from the nearest plausible parent
- `FAIL`: detail is more than 8 cm from a plausible parent, or is visibly floating
- `FAIL`: light/display/control has no housing/backplate/bracket within 15 cm

Report examples:

```text
FAIL SDP1_Iter8_Cockpit_Right_SideDisplayButtonBank_03
  role: display_or_control
  nearest_parent: SDP1_Iter6_Cockpit_Right_LargeSideLinerPanelA
  distance: 0.19m
  reason: display/control detail has no supporting panel contact

WARN SDP1_Iter7_CargoCeiling_LinerPanelLeft_02
  role: ceiling_panel
  nearest_parent: cargo ceiling rib
  distance: 0.045m
  reason: small gap may be acceptable but should be reviewed
```

### 3. Structural Coherence Audit

The pipeline should distinguish real structure from loose decoration.

Checks:

- ribs should connect between meaningful surfaces or terminate into caps
- rails should have supports or brackets at intervals
- light housings should have backplates or recesses
- panels should have surrounding seams, trims, or neighboring modules
- cables/conduits should terminate into equipment, panels, trays, or sockets
- large wall/ceiling/floor surfaces should have thickness, bevels, or layered construction

Acceptance:

- no major rib, rail, cable, or fixture appears unsupported
- repeated modules share spacing and alignment
- large interior surfaces have visible construction logic

### 4. Lighting Logic Audit

Every real Godot/Blender light should be tied to a visible fixture.

For each light:

- locate the nearest emissive lens or fixture
- verify the light origin is near the fixture
- verify the light direction points away from the fixture and toward a plausible target
- verify range and cone angle are localized enough for practical lighting
- flag broad fills that do not correspond to visible sources

Initial thresholds:

- `PASS`: light is within 30 cm of a matching visible fixture
- `WARN`: light is 30-75 cm from a visible fixture
- `FAIL`: light has no visible fixture within 75 cm
- `FAIL`: spotlight direction points into a wall, behind the fixture, or through solid hull
- `WARN`: omni or area light is broad enough to read as ambient wash

Acceptance:

- visible bright areas have nearby sources
- dark areas are shaped by practical lights, not hidden debug fill
- exterior light does not leak through closed hull/interior walls except through intentional openings or glass

### 5. Material Family Audit

The pipeline should report whether the ship has enough material-family separation and whether material assignment is coherent.

For each region, summarize:

- material family counts
- object area or approximate bounding volume by material
- roughness/metallic/emissive ranges
- dominant material percentage
- repeated use of placeholder flat colors

Initial target families:

- dark structural metal
- lighter wall/ceiling panels
- brushed/scratched metal
- rubber/gasket trim
- worn floor plates
- smoked glass/canopy
- seat fabric
- emissive indicators and light lenses

Acceptance:

- no major region is dominated by one flat material family
- materials are assigned by function, not random color
- emissive materials are limited to lights, displays, and indicators
- glass/canopy and rubber/gaskets remain visually distinct

### 6. Full-Spatial Evidence Generation

The pipeline should produce evidence that covers the whole model, not only a walkthrough.

Required evidence:

- orthographic front/side/top section sheets
- cargo bay 360 orbit contact sheet
- cockpit 360 orbit contact sheet
- ramp/entry 360 orbit contact sheet
- material-ID contact sheet
- unlit/albedo contact sheet
- normal/debug contact sheet
- light-only or emissive-only contact sheet if feasible

These views should be generated from deterministic camera rigs around region centers, not hand-picked flattering angles.

Acceptance:

- every major region is visible from multiple directions
- section/orthographic evidence exposes floating or misaligned detail
- material-ID evidence makes material-family problems obvious

## Pipeline Outputs

The first implementation should write:

- `reports/prototype_shuttle_visual_eval/interior_visual_eval_report.json`
- `reports/prototype_shuttle_visual_eval/interior_visual_eval_report.md`
- `reports/prototype_shuttle_visual_eval/interior_visual_eval_contact_sheet_current.png`
- `reports/prototype_shuttle_visual_eval/interior_region_orbit_contact_sheet_current.png`
- `reports/prototype_shuttle_visual_eval/material_id_contact_sheet_current.png`
- `reports/prototype_shuttle_visual_eval/attachment_debug_overlay_current.png`

The Markdown report should lead with failures:

```text
# Prototype Shuttle Interior Visual Evaluation

Status: FAIL

## Blocking Issues

- 14 objects appear floating or unsupported.
- 9 visible light fixtures have no matching actual light.
- 4 actual lights have no visible fixture.
- cockpit side sweep region is dominated 72% by near-black material.

## Region Summary

Ramp: WARN
Cargo Bay: PASS
Stairs/Landing: WARN
Cockpit: FAIL
```

## Implementation Plan

### Step 1: Blender Object Inventory

Create a Python tool:

- `tools/blender/evaluate_prototype_shuttle_interior_visuals.py`

It should:

- open the source `.blend`
- collect interior objects
- classify objects by name/material/collection
- write object inventory JSON
- compute bounding boxes, centers, dimensions, materials, and collection names

Acceptance:

- report includes every visible interior object
- generated objects and authored objects are both included
- output is deterministic

### Step 2: Attachment And Floating Checks

Extend the Blender tool to compute nearest plausible parent surfaces.

Initial approach:

- use object bounding boxes for a coarse first pass
- classify large floor/wall/ceiling/panel objects as candidate parents
- compute object-to-parent bounding-box distance
- flag details that are too far from any plausible parent

Later improvement:

- use mesh BVH nearest-point queries for more precise attachment checks

Acceptance:

- obvious floating pieces are reported
- mounted details are not over-reported
- report includes enough object names and distances to make fixes actionable

### Step 3: Lighting/Fixture Checks

Inspect both:

- Blender light objects in the source
- Godot review lights in capture/debug scripts where practical

Initial implementation can start with Blender/exported fixture geometry:

- identify emissive materials and light fixture objects
- identify actual lights
- match lights to nearest fixture/emissive lens
- report missing pairings

Acceptance:

- light without source is flagged
- emissive source without actual light is flagged as warning
- broad/global lights are clearly labeled as review-only or fail production mode

### Step 4: Material Family Report

Map materials to families using material names.

Report:

- material family distribution per region
- emissive material count
- near-black dominance percentage
- objects with unknown material family

Acceptance:

- cockpit/cargo/ramp material-family problems are visible in the report
- unknown materials are listed

### Step 5: Region Orbit And Debug Captures

Add deterministic capture scenes/scripts for:

- cargo orbit
- cockpit orbit
- ramp orbit
- section/orthographic views
- material-ID/unlit views

These should complement, not replace, the existing moving walkthrough.

Acceptance:

- each region is shown from multiple directions
- evidence exposes floating detail and weak anchoring
- contact sheets are stable between runs

### Step 6: Integrated Review Command

Add or update a host script/profile:

- `scripts/evaluate-prototype-shuttle-visuals.sh`

Expected flow:

1. run Blender visual evaluation
2. export if needed
3. import Godot if needed
4. run region/debug captures
5. write final Markdown/JSON report
6. fail with nonzero exit if blocking visual coherence checks fail

Acceptance:

- one command produces the report and evidence
- CI/host MCP can run it
- failures are actionable

## V1 Implementation Notes

Implemented V1 repo-side entrypoints:

- `tools/blender/evaluate_prototype_shuttle_interior_visuals.py`
- `scripts/evaluate-prototype-shuttle-visuals.sh`

The shell entrypoint refreshes the prototype shuttle export by default, then runs
the Blender visual evaluator against the source `.blend`. Set
`REFRESH_PROTOTYPE_SHUTTLE=0` to evaluate the current source without a refresh.

The model-level gate is fast by default. It writes a deterministic spatial
projection sheet for region coverage. Set `VISUAL_EVAL_RENDER_REGIONS=1` when a
human-review pass needs slower rendered region orbit evidence.

The evaluator currently performs:

- object inventory across the `Interior` collection
- object role classification by name/material
- coarse AABB attachment/floating checks for detail objects
- light-to-visible-fixture proximity checks using the exported light report
- material-family distribution by region
- evidence brightness checks using the material walkthrough manifest
- deterministic region orbit evidence for ramp, cargo bay, stairs/landing, and cockpit
- diagnostic sheets for issue counts, attachment locations, and material-family distribution

The matching MCP profile is:

- `evaluate prototype shuttle visuals`

If the running MCP server does not list that profile yet, restart the host MCP
server so it reloads `agent-manager/docker-mcp/config.json`.

## Acceptance Criteria For Pipeline V1

Pipeline V1 is complete when:

- it inventories all prototype shuttle interior objects
- it classifies objects into useful design roles
- it flags obvious floating/unanchored objects
- it flags lights without visible sources and sources without lights
- it reports material-family distribution by region
- it produces at least one region orbit contact sheet
- it produces a Markdown report with blocking issues first
- it can be run from the host MCP bridge

## Non-Goals For V1

Do not attempt in V1:

- photorealism scoring
- AI image judgement
- final art direction grading
- automatic retopology
- automatic replacement of bad geometry
- perfect mesh-level collision/attachment analysis

The goal is practical production QA, not a universal art critic.

## How This Changes The Art Workflow

Old loop:

1. add visual detail
2. render walkthrough
3. human notices problems
4. repeat

New loop:

1. define design role for each detail family
2. add visual detail
3. run model-level visual evaluation
4. fix floating/unsupported/unlit/unclassified failures
5. generate region orbit/debug evidence
6. review walkthrough only after the model passes basic coherence checks

This should reduce slow manual discovery and prevent small decorative changes from accumulating without improving visual quality.
