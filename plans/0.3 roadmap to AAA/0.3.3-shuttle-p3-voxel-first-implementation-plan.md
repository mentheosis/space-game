# 0.3.3 Shuttle P3 Voxel-First Implementation Plan

## Purpose

Restart the production shuttle pipeline as `shuttle_p3` using a voxel-first
interior and traversal planning process.

The current `prototype_shuttle` proved several valuable ideas, especially
exterior skin fitting, interior volume extraction, floorplan discovery, runtime
Godot validation, and evidence review. It also proved that hand-authored or
partially procedural floors, stairs, ramps, and collision can still create too
much iteration churn when the traversal path is not discovered as one coherent
system.

`shuttle_p3` should restart from a cleaner asset boundary and use granular
voxel planning to discover:

- interior room volumes,
- entry ramp envelope,
- cargo floor,
- cargo-to-cockpit ascent route,
- stair or ramp geometry,
- landings,
- player capsule clearance,
- traversal collision surfaces.

The goal is to make walkable interior layout and collision a generated contract
derived from the hull volume, not an after-the-fact manual repair pass.

## Reset Boundary

Reuse only:

- the current manually scaled exterior skin from `prototype_shuttle`;
- the human-cut forward belly ramp doorway in that exterior skin;
- the ship scale implied by that accepted skin.

Do not carry forward:

- current `prototype_shuttle` interior mesh,
- current generated floors,
- current ramp object,
- current stair objects,
- current collision layout,
- current interior collision contract,
- current furnishings,
- current lighting,
- current cockpit chairs,
- current procedural structural detail,
- current traversal helper assumptions beyond normal player-controller limits.

The exterior skin may be copied into a new `shuttle_p3` source scene as the
starting hull reference. From that point forward, `shuttle_p3` owns its own
Blender source, contracts, generated reports, Godot package, evidence, and
validation outputs.

## Core Design Principle

Use collision-first traversal planning, then build visual detail around the
approved traversal contract.

For `shuttle_p3`, floors, ramps, stairs, and landings should not be guessed as
visual objects first. The pipeline should discover where a player capsule can
move inside the hull, generate a clean traversable surface network, validate it,
and only then create the visible interior architecture around that network.

This means the model can still have detailed visual stairs, ramp panels, ribs,
rails, furnishings, and wall structures, but the primary walkable collision
should come from a clean, validated traversal surface contract.

## Phase 0: Preserve Accepted Exterior Skin

Tasks:

- Identify the current `prototype_shuttle` Blender source containing the manual
  ramp doorway cut.
- Copy the accepted exterior skin into a new `shuttle_p3` Blender source scene.
- Remove or disable all current prototype interior, collision, furniture,
  lighting, stair, ramp, and debug geometry from the new source.
- Keep only the exterior hull skin, orientation, scale, origin convention, and
  doorway cut.
- Export an exterior-only package for review.

Acceptance:

- `shuttle_p3` starts with the accepted cut/scaled exterior skin.
- The ramp doorway is visibly present in the hull.
- No old prototype interior/collision artifacts remain in the `shuttle_p3`
  source scene.
- The exterior-only review matches the current accepted silhouette and scale.

## Phase 1: Voxel Occupancy And Interior Free-Space Extraction

Tasks:

- Create `shuttle_p3_voxel_config.json` with:
  - voxel size,
  - player capsule radius,
  - standing height,
  - crouch height if needed later,
  - clearance margins,
  - exterior skin source object,
  - doorway/ramp seed region,
  - expected cargo and cockpit rough regions.
- Voxelize the exterior skin into a ship-local occupancy grid.
- Classify voxels as:
  - exterior solid or near-solid hull,
  - outside free space,
  - enclosed interior free space,
  - doorway/opening boundary,
  - ambiguous thin-shell region.
- Flood-fill from outside through known openings to distinguish exterior void
  from enclosed interior void.
- Generate interior free-space evidence:
  - side projection,
  - top projection,
  - cross sections,
  - 3D debug voxel cloud or mesh.

Acceptance:

- The extracted interior free-space field visibly fits inside the exterior hull.
- The ramp doorway/opening is recognized as a boundary between outside and
  interior.
- Cargo and cockpit free-space regions are visible in the voxel evidence.
- Thin hull or canopy regions do not incorrectly become walkable interior space.

## Phase 2: Semantic Region Discovery

Tasks:

- Segment the interior free-space voxels into semantic candidates:
  - lower cargo deck volume,
  - raised cockpit deck volume,
  - transition/ascent volume,
  - entry/ramp threshold volume,
  - canopy/cockpit headroom volume.
- Fit prismatic or mesh-derived planning volumes to these regions.
- Validate player standing clearance in cargo and cockpit.
- Validate two-seat cockpit feasibility with pilot/copilot proxies.
- Validate that the cargo-to-cockpit transition has enough envelope for stairs,
  ramp, or hybrid ascent.

Acceptance:

- Cargo and cockpit regions are discovered from interior free space rather than
  placed by hand.
- The cockpit volume is large enough for two seats and player movement around
  them where intended.
- The lower cargo volume uses the belly mass of the hull.
- The transition volume connects cargo to cockpit without intersecting the ramp
  path.
- Human review approves the semantic regions before traversal geometry is
  generated.

## Phase 3: Voxel Traversal Graph

Tasks:

- Convert interior free-space voxels into a traversal graph for the player
  capsule.
- Each candidate standing location must satisfy:
  - capsule radius clearance,
  - head clearance,
  - floor support or generated support candidate,
  - no hull penetration.
- Connect neighboring cells by movement type:
  - flat walk,
  - small step,
  - stair step,
  - ramp slope,
  - drop,
  - blocked.
- Store movement thresholds:
  - max step height,
  - preferred step height,
  - max slope angle,
  - min stair tread depth,
  - min landing depth,
  - min route width,
  - max acceptable ceiling obstruction.

Acceptance:

- The graph can answer whether a player can move from outside ramp approach to
  cargo, then from cargo to cockpit.
- The graph reports why a route fails: clearance, excessive slope, missing
  support, insufficient landing, too narrow, or blocked.
- The graph is independent from the current prototype's manually discovered
  floorplan.

## Phase 4: Ramp And Ascent Discovery

Tasks:

- Discover the forward belly entry ramp as a generated traversal surface:
  - start at outside/platform approach,
  - end flush with cargo floor candidate,
  - stay within the cut doorway envelope,
  - avoid upward lips,
  - satisfy slope limits.
- Discover cargo-to-cockpit ascent candidates:
  - side stairs,
  - side ramp,
  - split/switchback stair,
  - compact central ladder-like route only if explicitly accepted later.
- Score candidates by:
  - successful connectivity,
  - low slope,
  - generous width,
  - clean landing at bottom and top,
  - minimal conflict with ramp path,
  - staying inside the hull,
  - avoiding awkward collision edges.
- Generate evidence overlays showing all candidate routes and selected route.

Acceptance:

- The selected ramp reaches cargo floor cleanly and fits the doorway cut.
- The selected cargo-to-cockpit ascent reaches the cockpit floor cleanly.
- Bottom and top landings are large enough for turning.
- The selected route does not block the main ramp/cargo flow.
- Human review approves the selected traversal route before detailed modeling.

## Phase 5: Traversal Surface Contract

Tasks:

- Convert selected voxel route into named traversal surfaces:
  - outside approach pad,
  - entry ramp,
  - ramp threshold,
  - cargo floor,
  - ascent lower landing,
  - ascent surfaces,
  - ascent upper landing,
  - cockpit floor,
  - seat approach surfaces.
- Prefer clean continuous collision where it improves feel:
  - one-piece ramp for the belly ramp,
  - broad landing surfaces,
  - stair visuals may use simplified collision if needed,
  - avoid tiny seams and hidden vertical lips.
- Export a machine-readable traversal contract with surface bounds, heights,
  adjacency, and route metadata.

Acceptance:

- Static traversal validation passes using the generated contract.
- The generated surfaces are visible in debug evidence.
- Every route transition has explicit adjacency data and clearance data.
- No traversal surface is arbitrary or manually guessed without being tied back
  to voxel free-space evidence.

## Phase 6: Godot Player-Controller Validation

Tasks:

- Build a `shuttle_p3` layout review scene.
- Add an actual `PlayerController` traversal replay for:
  - outside approach -> ramp,
  - ramp -> cargo,
  - cargo turnaround,
  - cargo -> ascent,
  - ascent -> cockpit landing,
  - cockpit landing -> pilot seat approach.
- Record route progress, grounded state, collision contacts, auto-step/helper
  events, and timeout points.
- Fail on:
  - stuck movement,
  - loss of grounded traversal beyond tolerance,
  - collision with a non-route blocker,
  - route checkpoint reached only by excessive tolerance,
  - helper usage above accepted limits.

Acceptance:

- The actual player controller can complete the route.
- The replay report shows enough evidence to diagnose failures.
- Any validation tolerance reflects player capsule size and route geometry, not
  a loose distance shortcut.
- Human playtest begins only after the automated replay passes.

## Phase 7: Interior Architecture From Approved Traversal

Tasks:

- Model cargo deck, cockpit deck, stairs/ramp, landings, rails, and structural
  walls around the approved traversal contract.
- Preserve clear player path widths.
- Add walls, floors, and ceiling as complete enclosing structures.
- Add visible support for floors and landings so they do not look like floating
  panels.
- Add visual ramp hinge/frame details aligned with the cut doorway.

Acceptance:

- Interior architecture follows the generated traversal route.
- Floors and stairs feel structurally supported.
- No visible detail blocks the route validated by the traversal contract.
- The ramp, cargo, ascent, and cockpit spaces read as one coherent ship
  interior.

## Phase 8: Art Detail, Materials, And Lighting

Tasks:

- Add cockpit and cargo details after traversal is stable.
- Use references in `plans/0.3 roadmap to AAA/0.3.2 references/`, especially:
  - cockpit references,
  - interior lighting/material reference,
  - `cargo_ramp_ref.jpg`.
- Add practical lights attached to metal surfaces.
- Add material separation:
  - exterior hull,
  - interior wall panels,
  - darker structural metal,
  - reflective floor panels,
  - rubber/gaskets,
  - canopy glass,
  - seat fabric,
  - emissive screens/indicators.

Acceptance:

- Visual detail does not compromise validated traversal.
- Lighting sources are visible and physically plausible.
- Materials have enough roughness/metallic/normal variation to avoid flat
  placeholder appearance.
- Evidence includes interior walkthrough, cockpit review, ramp/cargo review, and
  collision overlay review.

## Phase 9: Main Game Integration

Tasks:

- Package `shuttle_p3` as a new ship asset alongside existing ships.
- Add it to the main game landing platform without replacing the old ships.
- Add entry/exit markers, cockpit seats, sit/stand, ship-local gravity, and
  basic flight integration.
- Validate:
  - ramp entry,
  - ship-local walking,
  - cockpit control,
  - sit/stand,
  - exterior collision/liftoff,
  - player handoff between ship gravity and planetary/space gravity.

Acceptance:

- `shuttle_p3` can be entered, traversed, piloted, exited, and flown in the main
  game scene.
- Old ships remain available for comparison.
- No special-case hacks from `prototype_shuttle` are required to make
  `shuttle_p3` traversable.

## Open Questions

- What voxel size should be used for the first pass?
  - Proposed: start at `0.25m`, then locally refine ramp/stair/landing areas to
    `0.10m-0.15m`.
- Should the belly ramp be discovered as a flat continuous ramp first, with
  visual paneling later?
  - Proposed: yes.
- Should cargo-to-cockpit use stairs, ramp, or let the voxel graph score both?
  - Proposed: score both, but prefer side stairs or a compact side ramp that
    does not block the belly ramp path.
- Should collision stairs be real steps or simplified ramp collision?
  - Proposed: let validation decide; visuals can be stairs, collision can be
    smoother if it produces better player feel.
- How much of the current `prototype_shuttle` export scripts should be copied
  versus generalized?
  - Proposed: copy only enough to get `shuttle_p3` moving, then generalize after
    the voxel-first process is proven.

## First Implementation Milestone

Milestone 1 should stop after Phase 2:

- copy accepted exterior skin into `shuttle_p3`,
- strip all old prototype internals,
- voxelize the hull,
- extract interior free space,
- discover semantic cargo/cockpit/transition/ramp regions,
- produce evidence for human review.

Do not proceed to generated floors, ramps, stairs, collision, or art detail
until the voxel-derived semantic regions are reviewed and accepted.
