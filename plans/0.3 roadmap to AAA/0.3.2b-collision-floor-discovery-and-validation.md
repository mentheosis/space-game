# 0.3.2b Collision Floor Discovery And Validation

## Purpose

The prototype shuttle now has an acceptable walkable path from the forward belly
ramp into the cargo deck and up to the cockpit. This took too many manual
iterations because the pipeline could generate visible collision surfaces, but
could not prove that the player capsule could traverse the route.

This pass adds a deterministic collision-floor discovery and validation process
so future layout changes can be generated, checked, and reviewed before manual
testing.

## Target Process

1. Extract ship exterior envelope and semantic interior volumes.
2. Generate candidate walkable collision surfaces for:
   - exterior-to-ramp transition,
   - ramp surface,
   - ramp-to-cargo edge,
   - cargo floor segments,
   - side stair/ascent lanes,
   - cockpit entry landing,
   - cockpit floor.
3. Export the generated collision layout as named machine-readable data.
4. Run static adjacency validation:
   - adjacent floor surfaces overlap enough for a player capsule,
   - vertical deltas stay within controller step limits,
   - ramps meet floor edges without upward lips,
   - stair lanes have continuous tread coverage,
   - top stair lanes connect to a landing that is deep enough not to overshoot,
   - landing overlaps the cockpit floor or intentionally becomes the cockpit
     entry floor.
5. Run real Godot traversal validation with the actual player controller.
6. Render evidence showing route nodes, collision surfaces, and pass/fail
   segments.
7. Only ask for manual playtest after automated checks pass.

## Current Implementation Scope

This first version implements steps 3, 4, and 5. It does not yet search over
many layout candidates.

The generator must export:

- named axis-aligned floor boxes,
- one-piece ramp contract,
- left and right stair treads,
- cockpit-entry landing,
- cockpit floor,
- route metadata and player clearance constants.

The validator must fail if:

- the ramp top is vertically above the cargo floor,
- the ramp top is too far below the cargo floor to walk smoothly,
- cargo floor segments do not overlap,
- stair tread height deltas exceed the controller step budget,
- stair treads have excessive horizontal gaps,
- the top stair does not overlap the cockpit-entry landing,
- the cockpit-entry landing does not overlap the cockpit floor,
- any required surface is missing.

The Godot traversal validator must fail if:

- the real `PlayerController` cannot reach each route checkpoint,
- the player loses grounded state for too long while traversing,
- the player times out before reaching the cockpit floor,
- the generated JSON contracts are missing required route surfaces.

## Prototype Shuttle Golden Baseline

The human-approved floorplan is a **prototype-shuttle-only calibration
artifact**. It is not a required step in the repeatable pipeline for future
ships.

For this prototype shuttle, the baseline is useful because it captures a
known-good answer discovered through manual playtesting. The discovery system
can use it to verify that candidate generation and validation are capable of
rediscovering or approximating a proven solution.

The baseline must include:

- generated collision layout JSON,
- static collision-layout validation report,
- real Godot traversal validation report,
- a short note describing what the baseline represents.

Future ships should not require a human-approved baseline before discovery can
run. The repeatable target flow remains:

`exterior/interior volumes -> candidate generation -> static validation -> real traversal validation -> scoring -> review`

The baseline is only a bootstrap aid for validating the prototype shuttle
algorithm.

## Next Expansion

After the static and traversal validators are stable, add a candidate search
loop:

- generate ramp hinge offsets and overlap variants,
- generate stair count/depth/side-lane variants,
- generate landing depth/width variants,
- score each candidate with the static validator,
- run the best candidates through the Godot traversal validator.

This turns manual collision iteration into:

`generate candidates -> validate -> score -> render evidence -> human review`

## Candidate Discovery V1

The first discovery runner uses an explicit `floorplan_candidate` object. The
generator can load it from `PROTOTYPE_SHUTTLE_FLOORPLAN_CANDIDATE` and emits the
active candidate into the generated collision layout report.

Candidate parameters currently include:

- `ramp_floor_edge_z_offset`
- `ramp_hinge_y_offset`
- `ramp_tip_y_delta`
- `ramp_tip_z_delta`
- `cargo_forward_floor_trim`
- `stair_count`
- `stair_depth_scale`
- `stair_width`
- `stair_lane_gap`
- `cockpit_entry_depth`
- `cockpit_entry_z_bias`

The discovery runner should:

1. Generate known-bad and grid-search candidate JSON files.
2. Rebuild/export each candidate.
3. Run package validation and static collision-layout validation.
4. Run Godot traversal validation on the strongest statically valid candidates.
5. Score candidates and report the selected passing candidate.
6. Compare the selected candidate to the prototype-only golden baseline.

The first success target is rediscovery of an equivalent passing floorplan, not
optimization beyond the human-approved baseline.
