# 0.3.2f Traversal Layout Audit Pipeline

## Purpose

The prototype shuttle now has enough interior complexity that screenshots,
walkthrough videos, and single-route Godot validation are not sufficient for
judging traversal quality. The player can fail because of small floor lips,
headroom, unclear stair geometry, wall/ceiling collision gaps, invisible
collision contradiction, or controller-helper behavior. These problems need
spatial evidence, not just camera evidence.

This pass adds a traversal layout audit pipeline that evaluates the ship
interior like a level-design and collision review tool.

## Position In The Pipeline

Run this gate after:

- exterior silhouette and volume lock,
- floor/collision candidate generation,
- static collision layout validation,
- exported Blender/Godot package validation.

Run it before:

- subjective walkthrough review,
- interior visual/detail iteration,
- ship flight/liftoff validation,
- manual playtest requests.

The intended order is:

`floorplan generation -> static layout validation -> traversal layout audit -> real controller replay -> human playtest`

The traversal audit does not replace manual testing. It reduces the number of
manual iterations by showing why a route is likely to feel wrong before a human
has to discover it by walking into it.

## Evaluation Layers

### 1. Capsule Clearance Samples

Sample the intended player route and evaluate the player capsule at each point.

For each sample:

- identify supporting floor/ramp/stair surface,
- compute floor height,
- compute head clearance to nearby ceiling/enclosure surfaces,
- compute lateral clearance between walls/guards when available,
- flag samples where the capsule is likely to clip, crouch, or feel cramped.

### 2. Surface Adjacency And Lip Audit

Evaluate every adjacent route surface pair.

Checks:

- horizontal overlap is wide enough for the capsule radius,
- vertical delta is within controller step budget,
- ramp-to-floor transition does not create a large upward lip,
- stair-to-landing transition does not require a jump,
- floor panels do not leave route gaps larger than the capsule can cross.

Classifications:

- `PASS`: continuous or comfortably walkable.
- `WARN`: traversable but likely needs controller assist or visual smoothing.
- `FAIL`: likely to block, snag, clip, or require jumping.

### 3. Controller Helper Budget

The game may use a vertical-only terrain traversal helper. The audit must make
that dependency explicit.

Report for each route transition:

- vertical delta,
- whether the base controller can traverse it unaided,
- whether the vertical helper is expected to be needed,
- whether the helper budget is exceeded.

The helper is allowed to correct small physical discontinuities, but the audit
should still flag surfaces that rely on it too frequently or too aggressively.

### 4. Contact Risk Visualization

Generate deterministic evidence that exposes the whole route:

- top-down route map,
- side profile showing floor heights and headroom,
- route samples colored by pass/warn/fail,
- transition markers where lips, gaps, or clearance failures occur.

This evidence is not intended to be pretty; it is intended to reveal the route.

### 5. Real Controller Replay

After the static audit passes, run the actual `PlayerController` through the
route and record:

- grounded state,
- velocity,
- step-helper activations,
- contact collider names,
- contact normals,
- stuck intervals,
- checkpoint reach/fail state.

The real replay remains necessary because geometry can be technically valid but
still feel poor.

## Outputs

Later implementation may add:

- contact heatmap images,
- Godot replay video,
- stuck-location timeline,
- playable route overlay scene.

## Acceptance Criteria

The traversal audit passes when:

- every required route surface exists,
- every adjacent route transition is `PASS` or accepted `WARN`,
- no head clearance sample falls below the player capsule height,
- no lateral clearance sample falls below capsule diameter plus margin,
- helper-required transitions remain within configured vertical helper budget,
- top and side evidence clearly show the intended route.

The audit fails when:

- a required route surface is missing,
- a route transition exceeds helper budget,
- floor/ramp/stair surfaces are disconnected beyond capsule tolerance,
- any sampled headroom is below player height,
- route geometry would force the player into a wall, ceiling, or guard.

## First Scope

The first version is a static Python audit over the exported prototype shuttle
layout and collision contracts. It intentionally avoids Blender/Godot runtime
dependencies so it can run quickly during iteration.

The first version should inspect:

- `prototype_shuttle_collision_layout_report.json`,
- `prototype_shuttle_markers.json`,
- `prototype_shuttle_interior_collision_contract.json`.

It should produce enough evidence to answer:

- where is the intended route,
- where does the route need vertical helper support,
- where is headroom tight,
- where are route transitions likely to snag,
- which issue should be fixed before another walkthrough or manual playtest.
