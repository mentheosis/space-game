# 0.3.2e Exterior Collision And Ship Physics Process

## Purpose

The prototype shuttle is now visible in the main game and has early pilot
controls, but the exterior collision and ship-world physics are not yet a real
asset-quality solution. The recent underside skid fix proved the problem: the
ship can be made to lift off with ad hoc support shapes, but that is not a
repeatable or high-quality exterior collision pipeline.

This phase establishes an exterior-focused multi-aspect iteration process,
equivalent in discipline to `multi-aspect-iteration-plan.md`, but aimed at the
ship exterior, world collision, player traversal, and flight physics.

## Goal

Create a prototype shuttle exterior collision package that:

- matches the visual hull closely enough to feel intentional;
- supports stable landing, liftoff, and planet/platform contact;
- lets the player traverse intended exterior surfaces without invisible
  contradictions;
- integrates ramp, hatch, interior volume, seat control, and ship gravity;
- can be generated, validated, and reviewed through repeatable tools rather
  than manual guessing.

The immediate target is still a vertical-slice prototype, not final production
collision, but the process should scale to future ships.

## Required Iteration Rule

Each exterior collision iteration must update all five aspects below before
running a review capture or asking for playtest feedback.

Before the review capture, write:

`plans/0.3 roadmap to AAA/exteriorhope_to_achieve_<iteration#>.md`

That document must include:

- the intended improvement for each aspect;
- why each change is large enough to matter;
- what evidence should prove or disprove the change;
- starting with iteration 2, a short review of whether the previous iteration
  actually achieved its stated goals.

Do not present a review artifact as successful unless the evidence addresses
all five aspects.

## Five Aspects

### 1. Visual-To-Collision Hull Fit

Collision must correspond to the exterior model, not just generic support
boxes.

Each iteration should improve at least one meaningful hull region:

- belly and underside;
- ramp door and hatch frame;
- wings and swept-back surfaces;
- nose and cockpit neck;
- rear body, engine area, and fins;
- exterior walkable hull surfaces.

Acceptance should be measurable:

- visible collision overlay does not extend more than `0.5m` beyond intended
  visual hull in primary review regions;
- no major visible hull surface intended for contact is missing collision;
- no invisible blocker crosses ramp, hatch, cockpit route, or intended walkway;
- collision groups are named semantically, not anonymously.

### 2. Ship-World Physics

The ship must behave as a physical object against planets and landing
platforms.

Each iteration should improve:

- landed support;
- liftoff without downward clipping;
- platform/planet collision response;
- stable resting orientation;
- preservation of ship momentum when pilot stands;
- no accidental spin or launch impulse from player interaction.

Acceptance should include:

- ship starts supported on the platform;
- pressing ascend from seated state produces upward motion, not downward
  clipping;
- if controls are released during early liftoff, the ship follows gravity and
  collision normally;
- ship does not tunnel through the planet or platform during low-speed contact;
- support shapes do not prevent ramp traversal or interior walking.

### 3. Player Exterior And Ramp Traversal

Player traversal must be validated separately from ship physics. The player
needs walkable surfaces, but those should not be confused with broad rigid-body
support shapes.

Each iteration should improve:

- platform-to-ramp transition;
- ramp-to-cargo transition;
- hatch opening clearance;
- exterior hull or wing surfaces intended to be walkable;
- safe transitions from ship-interior gravity to external gravity.

Acceptance should include:

- player can walk from platform to ramp to cargo deck without snagging;
- player can exit the ship by crossing the ramp/hatch boundary and inherits
  correct momentum;
- player can re-enter and regain ship-interior gravity based on location;
- visible collision debug overlay explains every contact surface;
- no step requires player jump unless explicitly intended.

### 4. Integration With Gameplay Systems

Exterior collision is only acceptable if it works with the actual game systems.

Each iteration should verify:

- hatch interaction;
- automatic interior-volume detection;
- ship-relative gravity frame;
- cockpit seat interaction;
- pilot camera and controls;
- debug overlay state reporting;
- old ship remains unaffected unless intentionally changed.

Acceptance should include:

- `F` interaction works at the prototype ramp and cockpit seat;
- sitting takes control of the prototype shuttle;
- standing returns the player to ship-interior gravity without kicking the ship;
- leaving the ship returns to planetary/space gravity and inherited momentum;
- `V` collision overlay remains useful for exterior troubleshooting.

### 5. Evidence And Validation

Every iteration must produce evidence that can catch failures before manual
playtest.

Required evidence targets:

- exterior collision overlay contact sheet;
- ramp and hatch close-up;
- underside/platform contact close-up;
- wing/hull walkability view if exterior traversal is part of the iteration;
- short liftoff validation or video from platform;
- static collision report listing named collision regions and bounds.

Required validation targets:

- Godot import;
- `dotnet build`;
- static collision contract validation via
  `scripts/validate-prototype-shuttle-exterior-collision.sh`;
- player traversal validation for platform -> ramp -> cargo -> cockpit;
- ship liftoff validation proving no immediate downward clip through platform
  via `scripts/validate-prototype-shuttle-liftoff.sh`.

Manual playtest should happen only after automated checks pass or after the
iteration explicitly states which automated check is not yet available.

## Collision Layer Strategy

Use separate semantic collision concepts even if they are exported together:

- **ship-world physics collision:** supports rigid-body contact with planet,
  landing platform, terrain, and future large obstacles.
- **player traversal collision:** supports walking on ramp, floors, stairs,
  exterior hull surfaces, and hatch transitions.
- **interaction volumes:** hatch, seat, and future exterior controls.
- **debug visual collision:** visible overlays, not gameplay blockers.

The process should avoid one huge invisible box around the ship because it
contradicts interior traversal. If broad support is needed, use shaped skids,
belly plates, or hull-following primitives placed outside playable interior
space.

## Deterministic Authoring Strategy

Preferred source of truth:

1. Blender source collections for authored exterior and collision objects.
2. Machine-readable collision contracts exported from Blender.
3. Godot loader consumes exported package and creates runtime nodes.
4. Godot-side emergency shapes are allowed only as temporary diagnostic fixes
   and must be migrated back into the Blender/export contract.

The current runtime underside skids are a temporary diagnostic bridge. This
phase should replace them with named exported ship-world physics collision
regions.

## Initial Phase Breakdown

### Phase E1: Collision Audit And Contract

Tasks:

- inspect current prototype shuttle exterior, interior, and collision reports;
- list all current runtime-only collision shapes;
- define named exterior collision regions;
- decide which regions are player-walkable versus ship-world only;
- add a static report that compares collision bounds against exterior bounds.

Acceptance:

- no anonymous or unexplained collision region remains in the target contract;
- temporary runtime skids are documented as temporary;
- review evidence shows current gaps before changes.

### Phase E2: Ship-World Physics Collision Generation

Tasks:

- author/export belly, skid, wing, nose, and rear support collision;
- remove or disable equivalent temporary Godot-side support once export exists;
- validate platform contact and liftoff with deterministic runtime evidence.

Acceptance:

- ship starts on platform without floating excessively;
- ascend liftoff does not clip downward;
- collision overlay aligns with exterior underside;
- player ramp path remains unobstructed;
- liftoff report records the number of contract physics shapes used and the
  lowest ship Y during launch, with no runtime Godot errors.

### Phase E3: Exterior Player Traversal

Tasks:

- author walkable ramp/hull/wing surfaces where intended;
- validate transition from platform to ramp to cargo;
- validate external walkable surfaces separately from flight collision.

Acceptance:

- player can traverse intended exterior surfaces;
- player does not collide with ship-world-only support shapes in normal routes;
- leaving/entering ship gravity frame works from location, not only hatch
  interaction.

### Phase E4: Gameplay Integration

Tasks:

- wire prototype ship HUD/settings where needed;
- make prototype seat, camera, and controls production-clean enough for manual
  flight testing;
- validate old ship and prototype ship can coexist.

Acceptance:

- both ships start on the platform without collision conflict;
- prototype shuttle can be entered, piloted, exited, and re-entered;
- controls and camera state are understandable.

## First Implementation Recommendation

Start with **E1 Collision Audit And Contract**. Do not continue tuning runtime
skids until the current collision inventory is explicit. The first useful output
should be:

- collision region contract JSON or Markdown table;
- current collision overlay evidence;
- list of temporary Godot-side collision additions;
- recommended exported Blender collision objects for E2.
