# 0.3.2 Production Prototype Shuttle

## Objective

Build a new Blender-first production prototype shuttle that can replace the current ShuttleA as the visual target.

The current ShuttleA remains the playable pipeline testbed. It should keep passing validation, but we should stop trying to polish it into the final-quality ship. The new shuttle should be authored from the beginning as a coherent asset package with exterior, interior, collision, markers, lights, scale proxies, materials, and evidence.

## Why Start Fresh

The current shuttle helped prove mechanics and pipeline ideas, but it carries too much prototype history:

- exterior model is an open-source placeholder/reference, not a ship designed for our gameplay needs
- interior was iterated through many procedural and Godot-side passes
- many visual nodes still exist manually in `Ship.tscn`
- physical collision and visual surfaces are still not a single authored product
- cockpit/interior quality improved but remains below the target quality bar

The pipeline is now strong enough to support a cleaner asset. Starting fresh should be faster than migrating every legacy visual and collision node.

## Process Correction: Restart At Shape Lock

The first generated `prototype_shuttle` blockout proved that the Blender export, package validation, Godot import, and evidence tools can work, but it did not prove the design. It should be treated as a pipeline smoke test, not as the visual or layout basis for the production shuttle.

The next production work must restart from **exterior silhouette and gross volume lock**. Do not iterate collision, traversability, hatch usability, material detail, or cockpit decoration until the exterior shape reads correctly in side, top, front, and three-quarter review. This is a hard gate because playable collision work against the wrong hull shape creates churn and makes the asset feel incoherent.

## Source-Of-Truth Correction

The prototype shuttle has now crossed from procedural blockout generation into authored Blender source. The saved source file at `assets/source/blender/ships/prototype_shuttle/prototype_shuttle.blend` contains a human-authored ramp doorway cut in the exterior hull that should be preserved.

Normal pipeline operations must export from the authored `.blend` and must not run the procedural bootstrap first. The procedural bootstrap is now a destructive regeneration tool only. It may be used for experiments or restarting the blockout, but only when explicitly requested with `PROTOTYPE_SHUTTLE_ALLOW_BOOTSTRAP_OVERWRITE=1` or through a review run with `PROTOTYPE_SHUTTLE_REGENERATE_BLOCKOUT=1`.

Practical rule:

- use `scripts/export-prototype-shuttle-blender.sh` for normal asset updates
- use `scripts/review-prototype-shuttle-blockout.sh` for validation/evidence against the authored source
- do not run `scripts/bootstrap-prototype-shuttle-blender.sh` unless intentionally discarding authored edits
- keep the manual doorway cut as current ground truth until a repeatable cutter/mesh-diff tool can reproduce it

## Product Target

Create a compact exploration shuttle suitable for early game exploration, but large enough to support a believable two-level interior.

The ship should support:

- two cockpit seats
- walkable lower cargo deck entered from a belly ramp
- forward-opening belly ramp/hatch under the large central hull volume that can later become animated
- short internal ascent from the cargo deck to the raised cockpit deck
- cockpit canopy with clear pilot sightline
- standing-height cargo and cockpit/cabin volume where practical
- believable exterior hull shape matching the interior volume
- underside/hatch lighting
- practical interior lighting
- simple but accurate collision
- future support for walkable exterior surfaces

The result does not need to be final shipping art, but it should feel like a serious vertical-slice game asset rather than a placeholder.

## Quality Bar

The new shuttle should aim for:

- coherent exterior silhouette with readable nose, canopy, wings/fins/landing posture, engines, and belly ramp/hatch
- interior that visibly fits inside the exterior shell
- canopy shape that matches both exterior and pilot view
- no arbitrary square frames, floating details, or visibly disconnected structural elements
- floor, wall, ceiling, cockpit, and hatch areas that feel enclosed and intentional
- material separation between hull metal, floor panels, trim, rubber/gaskets, glass, emissives, screens, and seat fabric
- localized practical lights with visible sources
- collision that supports traversal without invisible walls contradicting the visible model

## Non-Goals

- Do not port all current ShuttleA visual nodes one by one.
- Do not solve every final ship feature in this phase.
- Do not build a fleet system yet.
- Do not add animated ramp/hatch behavior yet unless it is cheap after the static model is correct.
- Do not use paid assets until we explicitly decide to evaluate paid libraries.
- Do not accept AI-generated meshes as final without cleanup, topology review, material review, and license/source notes.

## Source Strategy

Use a Blender-first approach with human review before committing to a direction.

Allowed sources:

- custom Blender blockout
- kitbash from free/open-source models with compatible licenses
- open-source model candidates reviewed before use
- generated concept images for reference only
- generated base meshes only as rough source material requiring cleanup

Preferred approach for this first production prototype:

1. Create a custom Blender blockout for exact scale, cockpit, hatch, and interior fit.
2. Add detail using reusable kitbash pieces.
3. Use open-source assets only when they clearly improve quality and licensing is documented.
4. Keep the whole asset editable in the Blender scene.

## Production Phases

### Phase 1: Art Brief And Scale Lock

Tasks:

- define target dimensions: length, width, height, lower cargo deck height, raised cockpit deck height, belly ramp width, and belly ramp height
- save 3-8 visual references for exterior/cockpit/interior/materials
- define player capsule, seated pilot proxy, and required interior clearance
- sketch or block rough side/top/front proportions in Blender

Acceptance:

- human approves the ship role and silhouette direction
- pilot, copilot, standing player, belly ramp, cargo deck, cockpit deck, and interior volume fit in the blockout
- cockpit canopy location is clear from the exterior shape

### Phase 2: Exterior Silhouette And Gross Volume Lock

Detailed plan: `0.3.2a-exterior-silhouette-and-volume-lock.md`

Tasks:

- restart the model from reference-constrained exterior massing
- model side, top, and front silhouette targets before adding gameplay collision
- lock the lower belly cargo mass, raised neck/cockpit mass, canopy location, wing/fins/engine stance, and belly ramp placement
- include transparent gross internal volume proxies for cargo deck, cockpit deck, ramp envelope, ascent envelope, standing proxies, and seated pilot/copilot proxies
- generate orthographic and three-quarter evidence focused on shape and volume fit

Acceptance:

- exterior silhouette clearly reads as a ShuttleA-inspired compact exploration shuttle with a lower belly cargo volume and raised forward cockpit/neck
- forward-opening belly ramp is located at the front of the belly/cargo mass, not at the rear and not directly under the cockpit nose
- cockpit/canopy volume is large enough for two seats and standing nearby where intended
- gross interior volumes visibly fit inside the hull in cutaway/transparent evidence
- human approves the shape before collision or playable traversal work resumes

Non-goal:

- Do not require player traversal, stair collision, or hatch interaction in this phase.

### Phase 3: Interior Architecture Lock

Tasks:

- convert approved gross volumes into a coherent lower cargo deck and raised cockpit deck layout
- place side ascent, stairs, or ramp route from cargo to cockpit
- place cockpit seats, pilot/copilot eye positions, canopy sightlines, and console envelope
- keep exterior shell visible as a fit reference

Acceptance:

- interior layout physically belongs inside the locked hull
- lower deck and upper cockpit deck are understandable before collision
- the ascent route is plausible and does not fight the ramp/cockpit placement
- cockpit sightlines align with canopy shape

### Phase 4: Traversal And Collision Blockout

Tasks:

- author collision collection for cargo floor, belly ramp, cockpit ascent, cockpit floor, seat obstacles, and simplified hull
- export collision GLB
- generate marker and scale proxy reports
- validate hatch-to-cockpit traversal path
- validate sit/stand positions against markers

Acceptance:

- player can walk from belly ramp to cargo deck to cockpit without snagging
- player can stand from seat without clipping into chair or stairs
- collision surfaces match visible walkable surfaces closely enough for MVP review
- collision is visibly inspectable in evidence

### Phase 5: Structural Detail Pass

Detailed plan: `0.3.2c-structural-detail-pass.md`

Tasks:

- add believable cockpit frame, canopy gasket, belly hatch frame, ramp edges, cargo-deck structure, cockpit ascent detail, ceiling ribs, wall structure, floor panels, handles, vents, and engine details
- keep details aligned to the hull shape rather than random decoration
- avoid blocking player traversal or sightlines

Acceptance:

- cockpit and canopy structure looks physically connected
- belly ramp/hatch reads as a real forward-opening mechanism
- interior has complete floor, walls, and ceiling
- details improve realism without visual clutter

### Phase 6: Material And Lighting Pass

Tasks:

- assign controlled PBR material families
- add practical light fixtures and matching light objects
- tune glass transparency and reflections
- tune roughness/metalness so floor and trim catch light without sparkling
- export material and light reports

Acceptance:

- material families read clearly at gameplay distance
- every bright light pool has an obvious nearby source
- cockpit view remains clear through canopy
- interior remains readable without broad ambient wash

### Phase 7: Godot Integration

Tasks:

- create a new Godot ship scene or package instance for the prototype shuttle
- reuse existing `ShipController`, hatch, pilot seat, interior volume, and validation systems
- load package markers/lights/proxies
- avoid hand-authoring major visual geometry in Godot
- keep ShuttleA intact as the fallback testbed

Acceptance:

- the new shuttle can be entered, traversed, piloted, stood up in, and exited
- package validation passes
- runtime validation passes
- current ShuttleA still validates

### Phase 8: Evidence And Human Review

Required evidence:

- exterior orbit/turntable MP4
- cockpit-focused MP4
- full interior walkthrough MP4
- belly ramp and cargo-to-cockpit route review MP4 or contact sheet
- collision overlay contact sheet
- scale proxy contact sheet
- package material/object report

Acceptance:

- current evidence aliases are generated
- only latest three timestamped artifacts are retained
- human can review exterior, interior, cockpit, hatch, collision, and scale without launching the game

## Validation Gates

The prototype shuttle is not accepted until:

- required collections exist
- required markers exist and are finite
- marker drift validation passes
- light drift validation passes
- scale proxy validation passes
- asset/material/light/proxy reports are generated
- collision export exists
- Godot C# build passes
- Godot import passes
- runtime ship validation passes
- evidence cleanup/index remains stable

## Migration Boundary

For the new prototype shuttle:

Keep in Godot:

- ship controller and physics root
- hatch and seat interaction logic
- interior volume logic
- camera/input behavior
- runtime UI/debug overlays

Move to package ownership:

- exterior visual mesh
- interior visual mesh
- cockpit/canopy geometry
- belly ramp/hatch visual geometry
- seat visual geometry
- physical collision proxies
- authored light fixtures and light data
- markers
- scale proxies
- review cameras

## Deliverables

- new prototype shuttle plan-specific source directory
- Blender source scene with required collections
- exported prototype shuttle package
- Godot integration scene or package instance
- validation scripts generalized beyond ShuttleA where needed
- review evidence with current aliases
- migration notes comparing the new prototype against ShuttleA

## Open Questions

- What ship id should we use: `prototype_shuttle`, `scout_shuttle`, or something more final?
- How large should the lower cargo deck be relative to the cockpit deck?
- Should the forward-opening belly ramp fold down as a single ramp, split into panels, or slide/hinge in a more spacecraft-specific way?
- Should the first prototype be symmetrical and conservative, or should we push for a more distinctive asymmetrical silhouette?
- Should we choose references before blockout, or start with a scale-first blockout and then select references?

## Recommended First Implementation Step

Start with `0.3.2a-production-shuttle-brief-and-blockout`.

That step should:

- choose ship id
- gather references
- define target dimensions
- create the first Blender scene with required collections
- place player/pilot/copilot/ramp/cargo-deck/cockpit-deck proxies
- create the rough exterior/interior blockout
- generate the first evidence contact sheet or viewport renders

Do not begin detailed modeling until the blockout proves the ship can physically contain the intended two-level interior, cockpit, belly ramp, cargo deck, cockpit ascent, and traversal path.
