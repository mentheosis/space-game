# 0.3.1 Ship Pipeline Foundation

## Objective

Build the first repeatable Blender-to-Godot ship asset pipeline.

The goal is not to finish a new ship. The goal is to make ship production systematic enough that future visual quality improvements happen in Blender asset packages, with automated export/import/review, instead of one-off Godot scene edits.

## Success Criteria

This phase is complete when:

- the current shuttle has a standardized Blender source scene structure
- Blender exports exterior, interior, collision, markers, and reports through scripts
- Godot can update the ship from exported assets without manual marker drift
- automated evidence is generated for exterior, cockpit, hatch, interior, collision, and scale
- stale artifacts are cleaned automatically
- validation catches missing markers, bad scale, and basic traversal regressions
- the process is documented well enough to repeat for a second ship

## Non-Goals

- Do not attempt a full AAA-quality ship rebuild in this phase.
- Do not select paid asset libraries yet.
- Do not deeply redesign ship gameplay.
- Do not hand-author large new visual sections directly in Godot.
- Do not treat generated AI meshes as production-ready without cleanup.

## Phase 1: Audit Current Ship Asset State

### Tasks

- Locate the current shuttle Blender scripts and generated GLB assets.
- Identify the current source of truth for:
  - exterior mesh
  - interior mesh
  - collision mesh
  - seat/hatch/camera markers
  - material overrides
  - review captures
- List which parts are authored in Blender and which are still authored only in Godot.
- Identify any Godot scene edits that should eventually become generated/imported.

### Deliverables

- `reports/ship_pipeline/current_asset_audit.md`
- list of manually authored Godot nodes that should migrate to the pipeline
- list of current generated files

### Acceptance

- We know exactly what is source-authored versus generated.
- We know which current ship features would be lost if Blender export regenerated the ship.

## Phase 2: Define Standard Ship Package Schema

### Required Blender Collections

- `Exterior`
- `Interior`
- `Collision`
- `Markers`
- `Lights`
- `ReviewCameras`
- `ScaleProxies`
- `Disabled_Source`

### Required Marker Names

- `seat_anchor`
- `pilot_eye`
- `seat_exit`
- `interior_spawn`
- `exterior_exit`
- `hatch_center`
- `ramp_start`
- `ramp_end`
- `collision_bounds`

### Required Export Files

- `ship_exterior.glb`
- `ship_interior.glb`
- `ship_collision.glb`
- `ship_markers.json`
- `ship_material_report.json`
- `ship_asset_report.json`

### Tasks

- Write the schema in a machine-readable format.
- Add validation rules for required collections and markers.
- Define coordinate conventions for Godot import.
- Define naming rules for material slots and collision objects.

### Deliverables

- `tools/ship_pipeline/ship_package_schema.json`
- `docs` or `plans` section explaining the schema

### Acceptance

- A script can fail fast if a required marker, collection, or export is missing.
- Marker names are stable and not tied to a single ship.

## Phase 3: Standardize Blender Source Scene

### Tasks

- Reorganize the current shuttle Blender scene into the standard collections.
- Add player standing capsule proxy.
- Add seated pilot proxy.
- Add cockpit camera proxy.
- Add hatch/ramp traversal path proxies.
- Add review cameras:
  - exterior front 3/4
  - exterior rear hatch
  - underside hatch lights
  - cockpit pilot view
  - interior hatch-to-cockpit
  - collision overlay
- Ensure all generated mesh object names are stable.

### Deliverables

- updated shuttle Blender source scene
- screenshots or renders proving collection organization
- scale proxy visible in review renders

### Acceptance

- Blender scene can be opened and understood without reading scripts first.
- Exterior/interior/marker/collision ownership is visually clear.
- Seat, cockpit, hatch, and ramp positions can be inspected in Blender.

## Phase 4: Export Scripts

### Tasks

- Add or update Blender script to export:
  - exterior GLB
  - interior GLB
  - collision GLB
  - marker JSON
  - material report
  - asset report
- Include object bounds for exterior, interior, and collision.
- Include triangle counts and material counts.
- Include missing UV/material warnings.
- Include marker transforms in ship-local coordinates.
- Include scale proxy measurements.

### Deliverables

- `tools/ship_pipeline/export_ship_package.py`
- updated host script wrapper
- exported package under `assets/models/ship/<ship_id>/`

### Acceptance

- One command exports the whole ship package.
- Export fails on missing required markers.
- Export warns on suspicious bounds, missing materials, or empty collections.

## Phase 5: Godot Import/Update Path

### Tasks

- Add a Godot-side import/update script or editor/runtime helper.
- Load exported marker JSON.
- Apply marker transforms to existing ship marker nodes.
- Replace or update exterior/interior/collision packed scenes.
- Keep gameplay scripts wired to stable node paths.
- Preserve intentionally authored Godot-only systems until they are migrated.
- Report any manual nodes that are not driven by the package.

### Deliverables

- Godot import/update script
- generated import report
- updated shuttle scene using exported package data

### Acceptance

- Re-exporting from Blender updates Godot marker positions.
- Seat, hatch, cockpit camera, and exit markers do not need manual scene edits.
- Existing gameplay still runs after import.

## Phase 6: Evidence Generation

### Required Evidence

- exterior turntable MP4
- cockpit pilot-view MP4
- rear hatch entry/exit MP4
- interior walkthrough MP4
- underside hatch lighting shot
- scale comparison contact sheet
- collision overlay contact sheet
- material/object report

### Tasks

- Standardize output directories.
- Generate `current` aliases for latest evidence.
- Keep only the latest 2-3 timestamped artifacts per evidence type.
- Add capture names that describe the purpose of the review.
- Remove redundant or confusing review modes.

### Deliverables

- updated review/capture scripts
- artifact cleanup script
- evidence output index

### Acceptance

- Human can review the ship package without launching the game.
- Evidence clearly shows what changed.
- Repeated validation does not create unbounded artifact history.

## Phase 7: Validation Gates

### Required Automated Checks

- required Blender collections exist
- required markers exist
- marker transforms are finite and plausible
- player capsule fits through hatch-to-cockpit route
- seated pilot proxy fits under canopy
- cockpit view exits through canopy/window, not opaque geometry
- interior spawn is inside cabin and not clipping hatch geometry
- seat exit is behind chair and supported by walkable collision
- exterior/interior bounds overlap plausibly
- collision bounds do not grossly exceed visual bounds
- Godot C# build passes
- Godot runtime validation passes

### Deliverables

- validation script additions
- host MCP profile updates if needed
- validation checklist in report output

### Acceptance

- Pipeline errors are caught before manual playtest.
- Validation output explains the failed marker/object/check clearly.

## Phase 8: Documentation And Operator Workflow

### Tasks

- Document the one-command workflow.
- Document expected host MCP profiles.
- Document where exported files go.
- Document how to inspect evidence.
- Document how to add a new ship.
- Document what still requires human review.

### Deliverables

- `docs/ship_pipeline.md` or plan appendix
- updated `AGENTS.md` notes if new MCP profiles are added
- command examples

### Acceptance

- A future agent can run the pipeline without rediscovering the host setup.
- A human can understand what was generated and what needs review.

## Risks

- Current shuttle scene may have too many Godot-authored pieces to migrate cleanly in one pass.
- Blender generated geometry may still be too procedural-looking without a real kitbash library.
- Marker updates can break gameplay if node paths are not stable.
- Collision and visual alignment may need a more explicit authoring convention.
- Review artifacts can become noisy unless cleanup is enforced.

## Open Questions

- Should the current shuttle remain the pipeline test asset, or should we use a new cleaner ship candidate?
- Should exterior hatch lights and other recent Godot-authored fixtures migrate into Blender now or later?
- Should material authoring remain Blender-only for v1, or should we prepare for Substance/ArmorPaint integration?
- Should Godot import be an editor tool, a script run by host profile, or both?

## Recommended Execution Order

1. Audit current asset ownership.
2. Define schema and required markers.
3. Reorganize Blender scene.
4. Export package reports.
5. Import marker/package data into Godot.
6. Standardize evidence generation and cleanup.
7. Add validation gates.
8. Document workflow.

This order prioritizes repeatability before another major art pass.
